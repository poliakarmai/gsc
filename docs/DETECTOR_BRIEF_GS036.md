# DETECTOR BRIEF — GS036

## 1. Состояние

Детектор GS036 покрывает 19 категорий Node.js-уязвимостей. Основная проблема — **широкие регулярные выражения без учёта контекста**, что приводит к FP в следующих сценариях:

- **Тестовый код** — паттерны срабатывают на `req.body` в тестах (supertest, jest), где это просто мок-объект.
- **Именование переменных** — `req` может быть не объектом HTTP-запроса, а локальной переменной (например, `const req = { body: ... }`).
- **Комментарии и строки** — regex не исключает закомментированный код и строковые литералы.
- **Символьные константы** — `dangerouslySetInnerHTML` и `algorithm: "none"` могут быть в конфигурационных файлах или литералах, не связанных с реальным выполнением.
- **Переменные, не являющиеся пользовательским вводом** — `req.body` в middleware, где `req` — это уже обработанный объект.

---

## 2. FP root-cause (по группам)

### Группа A: Ложные срабатывания на тестовом коде
- **Причина**: Паттерны не различают продакшн-код и тесты. `req.body` в тестах (например, `supertest` или `jest`) — это мок-объект, не содержащий реального пользовательского ввода.
- **Пример**: `it('should return 200', async () => { const res = await request(app).post('/api').send({ body: req.body }); })` — сработает `command_injection_exec`.

### Группа B: Ложные срабатывания на локальных переменных с именем `req`
- **Причина**: Паттерны жёстко завязаны на имя `req`, но в коде могут быть локальные переменные с тем же именем, не являющиеся HTTP-запросом.
- **Пример**: `const req = { body: userInput }; exec(req.body)` — сработает `command_injection_exec`, хотя `req` — это просто объект.

### Группа C: Срабатывание на закомментированном коде и строках
- **Причина**: Regex не исключает комментарии (`//`, `/* */`) и строковые литералы. Например, `// eval(req.body)` или `const s = "exec(req.body)"` — оба вызовут FP.

### Группа D: Символьные константы в конфигурационных файлах
- **Причина**: `jwt_none_algorithm` срабатывает на `algorithm: "none"` в любом контексте, включая конфигурационные файлы или документацию. `dangerouslySetInnerHTML` — на любом JSX-атрибуте, даже если это статическая строка.

### Группа E: Переменные, не являющиеся пользовательским вводом
- **Причина**: `req.body` может быть уже валидированным/санитизированным объектом, но паттерн не проверяет, что это действительно необработанный ввод.

## 3. Precision-фиксы (таблица)

| Root-cause | Фикс | FP-срез | TP-риск |
|---|---|---|---|
| **A: Тестовый код** | Добавить фильтр `_is_test_file(file_path)` — исключать файлы с `test`, `spec`, `__tests__` в пути (аналогично `EXCLUDE_PATH_RE`). | **Высокий** | **Низкий** (тестовые файлы не должны быть в проде) |
| **B: Локальные переменные `req`** | Добавить проверку `_is_http_request_var(content, match)` — искать в контексте строки `app.use`, `router.post`, `function handler(req, res)` или `(req, res) =>`. Если `req` не является параметром функции-обработчика — пропустить. | **Средний** | **Средний** (может пропустить TP, если `req` переименован, но это редкий случай) |
| **C: Комментарии и строки** | Добавить фильтр `_is_comment_or_string(content, match.start())` — проверять, не находится ли match внутри `//`, `/* */`, `'...'`, `"..."`, `` `...` ``. | **Высокий** | **Низкий** (реальный код не в комментариях) |
| **D: Символьные константы** | Для `jwt_none_algorithm` — добавить проверку, что `algorithm` находится в объекте `jwt.sign`/`jwt.verify` (например, `jwt.sign(payload, secret, { algorithm: "none" })`). Для `dangerouslySetInnerHTML` — проверять, что значение — не статическая строка (например, `{__html: "static"}` — FP, `{__html: userInput}` — TP). | **Средний** | **Средний** (может пропустить TP, если `algorithm` задан через переменную) |
| **E: Не-пользовательский ввод** | Для `command_injection_exec` и `path_traversal` — добавить проверку, что `req.body`/`req.query`/`req.params` не присвоены переменной с именем `sanitized`, `validated`, `clean` (например, `const clean = req.body; exec(clean)` — FP). | **Средний** | **Низкий** (такие переменные обычно уже обработаны) |

## 4. Требует pro-проверки

1. **Фикс B (проверка `req` как параметра)** — сложно реализовать без полноценного AST-парсера. Regex-подход может дать ложные срабатывания на стрелочных функциях без скобок. Требует ручной валидации на реальном коде.
2. **Фикс D (контекст `jwt.sign`)** — regex не может надёжно определить, что `algorithm` относится именно к `jwt.sign`, если объект передаётся через переменную. Возможно, потребуется двухпроходный анализ.
3. **Фикс E (имена переменных)** — список «безопасных» имён (`sanitized`, `validated`) может быть неполным. Нужно собрать статистику по реальным FP.

---

## 5. Рекомендуемая последовательность

1. **Сначала фикс C (комментарии/строки)** — самый безопасный, не влияет на TP, даёт максимальный FP-срез.
2. **Затем фикс A (тестовые файлы)** — простой фильтр по пути, аналогичный `EXCLUDE_PATH_RE`.
3. **Фикс D (символьные константы)** — точечные правки для `jwt_none_algorithm` и `dangerouslySetInnerHTML`.
4. **Фикс E (не-пользовательский ввод)** — добавить фильтр по именам переменных.
5. **Фикс B (локальные `req`)** — самый рискованный, требует pro-проверки. Реализовать в последнюю очередь, после сбора статистики по FP.

---

### Примечание

Все фиксы должны быть реализованы как **дополнительные фильтры** (функции `_is_comment_or_string`, `_is_test_file`, `_is_http_request_var`, `_is_sanitized_input`), вызываемые внутри цикла `for match in re.finditer(...)`. Это не изменит `rule_id`, `finding_key`, `severity` и не перепишет детектор целиком.
