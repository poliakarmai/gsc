# Дорожная карта: тестовая методология детекторов GSC

> Источник: книга «Тестирование программного обеспечения. Базовый курс» (Куликов, 3-е изд., EPAM 2024).
> Анализ применимости к GSC (SAST, 47 детекторов, precision/recall/FP-rate).
> **Цель:** снижать FP без потери recall, повышать доверие к детекторам.
> Легенда статусов: ✅ внедрено · 🔧 внедряется · 📋 запланировано · 🔭 направление (без конкретного тикета).

Ключевая аналогия всей дорожной карты: **FP детектора = дефект детектора**.
precision = позитивное тестирование (recall), clean-проекты = негативные тесты (FP-rate),
vuln-проекты = error seeding / мутационное тестирование.

---

## A. Метрики и доверие (семантика recall/precision)

| # | Заимствование (раздел книги) | Применение в GSC | Статус |
|---|---|---|---|
| A1 | Тестирование показывает наличие дефектов, а не их отсутствие (2.1.3) | recall формулировать как «доля найденных ИЗВЕСТНЫХ уязвимостей», не «нашли всё»; precision не доказывает «правильность» | ✅ (в отчётах precision/recall) |
| A2 | Исчерпывающее тестирование невозможно (2.1.3) | calibration-сеть = репрезентативные классы эквивалентности кода, не «больше проектов» | ✅ (13 проектов) |
| A3 | Отсутствие дефектов — не самоцель (2.1.3) | не оптимизировать детектор ради метрики; целевая функция — полезный сигнал при приёмлемом шуме | 🔭 |
| A4 | Тестирование зависит от контекста (2.1.3) | precision/recall считать в разрезе (язык × фреймворк × класс), не одним средним числом | 📋 |
| A5 | Мутационное тестирование / error seeding (2.3.2.13) | 4 vuln-проекта = seeded-корпус; recall = доля засеянных уязвимостей; экстраполяция «сколько ещё не видим» | ✅ (основа) / 🔭 (оценка полноты) |
| A6 | Позитивное vs негативное тестирование (2.3.2.7) | clean = негативные тесты («пройден = детектор промолчал»); vuln = позитивные; негативные не объединять → FP считать по каждому срабатыванию | ✅ |

## B. FP-лог = отчёт о дефекте

| # | Заимствование | Применение в GSC | Статус |
|---|---|---|---|
| B1 | Цепочка ошибка→дефект→сбой (2.5.1) | `fp_log` фиксирует root cause (`pattern_id` + `reason`), а не только проявление (`finding_key`) | 🔧 |
| B2 | Три цели отчёта о дефекте (2.5.2) | `reason`=информация, severity/частота=приоритет, `action_taken`=содействие устранению | ✅ |
| B3 | Жизненный цикл дефекта (2.5.2) | статусы FP: `detected → verified → resolved / reopened` + резолюции («это TP», «дубликат», «не воспроизводится», «отложен») | 📋 (требует миграции схемы) |
| B4 | Атрибуты отчёта (2.5.3) | добавить `expected_behavior`/`why_not_vuln` (Exp — почему код безопасен) и `reproducibility` | 📋 (миграция) |
| B5 | Качественный отчёт = 1 дефект = 1 причина (2.5.5) | 1 запись fp_log = 1 FP с одной причиной; дедуп по `finding_key` | 📋 |
| B6 | «Дефекты проявляются группами» (2.5.6) | при подтверждении FP сканировать соседние findings того же `pattern_id` на тот же root cause | 🔭 |

## C. Тест-корпус = тест-кейсы

| # | Заимствование | Применение в GSC | Статус |
|---|---|---|---|
| C1 | Чек-лист как требования (2.4.1) | `test_corpus.py` → матрица покрытия `rule_id × язык × конструкция × граничный случай` | 📋 |
| C2 | Минимум тест-кейса (2.4.2) | критерий теста: фиксированный snippet + точный `finding` (`rule_id`+`line`+`finding_key`) + явная цель | 📋 |
| C3 | Жизненный цикл тест-кейса (2.4.2) | статусы тестов `active/needs_update/deactivated`; деактивация паттерна → его TP-тесты в `deactivated`, не удалять | 📋 |
| C4 | Свойства качественных тестов (2.4.5) | атомарность (1 тест = 1 паттерн), неизбыточность (классы эквивалентности), повторяемость (детерминированные входы), прослеживаемость | 🔧 |
| C5 | **Демонстративные assert'ы (2.4.5)** | assert на конкретный `finding_key`/`title`/`rule_id`, а не `len(findings)==1` | 🔧 (t16 уже усилен) |
| C6 | Классы эквивалентности + граничные условия (2.7.2) | fixture на каждый класс входных строк (`eval`/`exec`/`Function`/`constructor`) + границы regex (`\b`, квантификаторы, экранирование, пустая строка) | 📋 |
| C7 | «Ввод искусственных ограничений — плохо» (2.7.2) | не править regex «под калибровку»; сужение проверять против recall (vuln), не только clean | 🔭 |

## F. Процесс (принципы тестирования)

| # | Заимствование | Применение в GSC | Статус |
|---|---|---|---|
| F1 | Регрессионное тестирование (2.3.2.12) | каждая правка regex → полный перепрогон calibration (чистые + vuln), контроль recall | ✅ (обязательная процедура) |
| F2 | Re-testing / confirmation (2.3.2.12) | подтверждение каждого исправленного FP на том же образце | ✅ |
| F3 | Кластеризация дефектов (2.1.3) | отчёт FP по детекторам/паттернам, искать кластеры (80/20), бить точечно | 🔭 |
| F4 | Раннее тестирование / V-модель (2.1.1, 2.1.3) | тест-кейсы рождаются вместе с паттерном; мини-калибровка на 5–10 сниппетах до интеграции | 🔭 |
| F5 | Entry/exit criteria (2.1.2) | критерии готовности детектора: entry (спецификация+корпус), exit (precision/recall ≥ порога + re-testing) | 📋 |
| F6 | Тестирование требований (2.2) | спецификация детектора до regex: атомарность (1 класс уязвимости), недвусмысленность (антипримеры), проверяемость, прослеживаемость (↔ CWE ↔ тесты) | 🔭 |
| F7 | Peer review требований (2.2.6) | cross-review regex-паттернов до релиза («что этот паттерн на самом деле ловит?») | 🔭 |

## Приоритет внедрения (ближайшие шаги)

1. **E1 — guard авто-деактивации** (карантин CRITICAL) — прямое решение главной боли «снизить FP без потери recall».
2. **B1 — типизированный root-cause `reason`** — превращает `fp_log` из свалки в инструмент атрибуции.
3. **C5 — демонстративные assert'ы** — дешёвый рост ценности всех 673 тестов как guard'ов.
4. **B3 — жизненный цикл FP** (статусы) — миграция схемы `fp_log`, самый системный выигрыш.
5. **C6 / D3 — классы эквивалентности + попарная генерация** — систематизация calibration/benchmark.
6. **A4 — precision в разрезе** (язык × фреймворк) — точное знание, где реально шумит.
7. **E4 — KDT** (пороги в конфиг) — переиспользуемый trainer.

> Примечание: пункты с 🔧 внедряются кодом в текущей итерации; 📋 — конкретные тикеты;
> 🔭 — долгосрочные направления/процессы без жёсткого срока.
