# DETECTOR BRIEF — GS003

## 1. Состояние

Детектор GS003 находит debug-выражения (`print()`, `console.log`, `dbg!`, `println!`) в production-коде. Текущая реализация имеет **высокий уровень false-positive**, так как не учитывает:

- CLI-инструменты, где `print()` — легитимный вывод (частично покрыто `_is_cli_tool`, но фильтр слишком узкий);
- скрипты/утилиты, где `print()` — основная функция (не только CLI);
- библиотеки, где `print()` используется для user-facing сообщений (например, инструкции по установке);
- JS-код, где `console.debug` — осознанный выбор для отладки в браузере;
- файлы с `__description__` / `__doc__` — служебные метаданные, а не debug;
- однострочные скрипты (например, `app.py` с единственным `print("hello")`).

**Важно:** в выборке нет ни одного TP-примера, что подтверждает критический перекос в сторону FP.

---

## 2. FP root-cause (по группам)

### Группа A: CLI-инструменты и скрипты с легитимным выводом
**Примеры:** `clean_db/main.py`, `load_data/main.py`, `iam_sample_audit.py`, `app.py`, `contoh_workaround.py`, `edit_cron.py`
**Причина:** `_is_cli_tool()` не срабатывает, потому что:
- файл не содержит `argparse`/`click`/`typer`, но является скриптом с `if __name__ == "__main__"`;
- файл — модуль, вызываемый из CLI-обёртки (например, `actions/aws/clean_db/main.py`);
- файл — простой скрипт без стандартных CLI-библиотек.

### Группа B: User-facing сообщения в библиотеках
**Примеры:** `providers.py` (строки 137, 147, 157 — "Install pip install..."), `base.py` (строки 305–310 — "Here are some examples:"), `session_auth/commands.py` (строки 10, 13)
**Причина:** `print()` используется для вывода инструкций, примеров, статусов — это часть API/UX, а не debug.

### Группа C: Служебные метаданные и форматирование
**Примеры:** `main.py:18` (`print(os.path.basename(...) + " : " + __description__)`), `iam_sample_audit.py:123` (`print("\n"+cypher['Description'],"\n")`), `iam_sample_audit.py:136` (`print("\n")`)
**Причина:** вывод описаний, заголовков, пустых строк — это форматирование отчёта, а не debug.

### Группа D: JS-код с осознанным `console.debug`
**Пример:** `webauthn.js:311` — `window.console.debug("[django-mfa] passkey autofill:", err)`
**Причина:** `console.debug` — намеренный уровень логирования (ниже `console.log`), часто используется в библиотеках для отладки по требованию.

### Группа E: Обработка ошибок через `print`
**Пример:** `controls_repo.py:44` — `print(f"Problem reading control json files: {e}")`
**Причина:** вывод ошибки пользователю/в лог — легитимная практика в скриптах без logging.

### Группа F: Простые скрипты-примеры
**Пример:** `app.py:1` — `print("hello")`
**Причина:** файл — демонстрационный скрипт, не production-код.

## 3. Precision-фиксы (таблица)

| # | Root-cause | Фикс | FP-срез | TP-риск |
|---|-----------|------|---------|---------|
| 1 | **Группа A** — CLI-скрипты без стандартных библиотек | **Расширить `_is_cli_tool()`**: добавить проверку на `if __name__ == "__main__"` **в сочетании** с вызовом `print()` на верхнем уровне (не внутри функции). Также добавить паттерн `sys.argv` (обращение к аргументам CLI). | **Высокий** (покрывает ~40% FP) | **Низкий** (CLI-скрипты с debug-print внутри функций останутся) |
| 2 | **Группа B** — user-facing сообщения | **Добавить фильтр `_is_user_facing_message()`**: пропускать `print()` если аргумент — строковый литерал, содержащий: `"Install"`, `"pip install"`, `"Here are"`, `"Removing"`, `"Successfully"`, `"Usage:"`, `"Example"`, `"Error"`, `"Warning"`. Реализация — regex по содержимому строки. | **Средний** (~15% FP) | **Средний** (возможен пропуск debug-сообщений с такими словами, но это редкий случай) |
| 3 | **Группа C** — служебные метаданные | **Добавить фильтр `_is_metadata_output()`**: пропускать `print()` если аргумент содержит `__description__`, `__doc__`, `__title__`, или если аргумент — только `"\n"` / пустая строка / `os.path.basename(...)`. | **Средний** (~10% FP) | **Низкий** (debug-код редко выводит метаданные) |
| 4 | **Группа D** — `console.debug` в JS | **Сужение паттерна**: изменить `console\.(?:log\|debug\|trace\|dir)` на `console\.(?:log\|trace\|dir)` — убрать `debug`. Альтернатива: оставить `debug`, но добавить фильтр `_is_browser_library()` (проверка на `window.` перед `console.debug`). | **Средний** (покрывает все JS-FP) | **Низкий** (console.debug — редкий debug-паттерн, обычно используют `console.log`) |
| 5 | **Группа E** — обработка ошибок | **Добавить фильтр `_is_error_output()`**: пропускать `print()` если аргумент содержит `{e}`, `{err}`, `{error}`, `"Error"`, `"Failed"`, `"Problem"`, `"Exception"`. | **Средний** (~5% FP) | **Средний** (debug-код иногда выводит ошибки, но обычно через `logging.exception`) |
| 6 | **Группа F** — простые скрипты | **Добавить фильтр `_is_simple_script()`**: пропускать файл, если он содержит ≤ 20 строк и ≤ 3 `print()` вызовов. Реализация — подсчёт строк и `print`-вхождений. | **Низкий** (~5% FP) | **Низкий** (production-файлы редко настолько малы) |
| 7 | **Группа A** — модули, вызываемые из CLI | **Добавить фильтр `_is_cli_module()`**: пропускать файл, если путь содержит `actions/`, `commands/`, `cli/`, `scripts/`, `tools/` **и** файл не содержит классов/функций с бизнес-логикой (эвристика: нет `def ` на верхнем уровне). | **Средний** (~10% FP) | **Средний** (возможен пропуск debug в таких модулях) |

## 4. Требует pro-проверки

1. **Фикс #1 (расширение `_is_cli_tool`)** — нужно проверить на реальных TP: не пропустит ли он debug-`print()` внутри `if __name__ == "__main__"` в production-скриптах (например, в `manage.py` Django).
2. **Фикс #2 (user-facing сообщения)** — риск пропуска debug-сообщений вида `print("Error: ...")` в коде, где это действительно debug. Нужен анализ частоты таких паттернов.
3. **Фикс #4 (console.debug)** — если убрать `debug` из паттерна, нужно убедиться, что нет TP с `console.debug` в production-коде (например, в браузерных библиотеках, где это единственный способ отладки).
4. **Фикс #7 (CLI-модули)** — эвристика «нет `def` на верхнем уровне» может быть ненадёжной. Нужно проверить на реальных проектах.
5. **Общий вопрос:** в выборке нет TP — нужно собрать эталонный набор TP для проверки, что фиксы не снизят TPR ниже допустимых 97%.

## 5. Рекомендуемая последовательность

1. **Сначала — фикс #4** (console.debug) — самый безопасный, низкий TP-риск, покрывает все JS-FP.
2. **Затем — фикс #1** (расширение `_is_cli_tool`) — самый большой FP-срез, но требует pro-проверки.
3. **Потом — фикс #3** (метаданные) — точечный, низкий риск.
4. **Далее — фикс #5** (обработка ошибок) — средний FP-срез, умеренный риск.
5. **После — фикс #2** (user-facing) — средний FP-срез, но выше TP-риск.
6. **В конце — фиксы #6 и #7** (простые скрипты, CLI-модули) — как дополнительные фильтры, после проверки первых четырёх.

**Важно:** после каждого фикса — прогон на эталонном наборе TP/FP и контроль TPR ≥ 97%.
