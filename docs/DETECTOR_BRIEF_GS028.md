# DETECTOR BRIEF — GS028

## 1. Состояние

Детектор GS028 — это **обёртка над внешним движком инвариантов** (`InvariantEngine`). Сам детектор не содержит паттернов, regex или эвристик — он лишь транслирует результаты `engine.verify_file()` в формат находок GSC.

**Критическое наблюдение:** детектор не имеет собственной логики фильтрации. Все FP/TP определяются качеством `InvariantEngine` и конфигурацией `.gsc-audit.yml` в репозитории. Это означает, что precision-фиксы должны быть направлены на **интерфейсную прослойку** — валидацию входных данных и пост-обработку результатов движка.

**Текущее состояние:** нет ни одного помеченного FP или TP, нет выборки шума. Это делает невозможным эмпирическую группировку root-cause. Ниже — гипотетические группы, основанные на типовых ошибках движков инвариантов.

---

## 2. FP root-cause (по группам)

### Группа A: «Мёртвые» инварианты (неприменимые к файлу)
Движок может возвращать нарушения инвариантов, которые не применимы к данному типу файла или языку. Например, инвариант «все SQL-запросы параметризованы» срабатывает на `.md`-документации, где SQL встречается в примерах кода.

### Группа B: Инварианты с неполным контекстом (ложные срабатывания на «сырых» данных)
Движок может проверять инварианты на необработанном `content`, не учитывая комментарии, строковые литералы или мёртвый код (dead code). Например, инвариант «запрещён `eval()`» срабатывает на `eval()` внутри строки документации или в закомментированном коде.

### Группа C: Дублирование находок (один инвариант — несколько срабатываний)
Движок может возвращать несколько нарушений одного инварианта на одной строке (например, при множественных вхождениях паттерна в строку). Это не FP в строгом смысле, но создаёт шум и снижает precision по метрике «находка/строка».

### Группа D: Инварианты с «мягкой» семантикой (неоднозначные правила)
Конфигурация `.gsc-audit.yml` может содержать инварианты, которые по своей природе недетерминированы (например, «используй только безопасные функции» без точного списка). Движок может срабатывать на легитимные альтернативы.

## 3. Precision-фиксы (таблица)

| Root-cause | Фикс | FP-срез | TP-риск |
|---|---|---|---|
| **A: Мёртвые инварианты** | Добавить фильтр `_is_applicable_language(invariant, language)`: проверять, что `invariant.languages` (если указано в метаданных) содержит текущий `language` или `"*"`. Если поле отсутствует — пропускать (не блокировать). | высокий | низкий (инварианты без языковой привязки не затрагиваются) |
| **B: Неполный контекст** | Добавить пост-фильтр `_is_in_active_code(file_path, content, v.line)`: проверять, что строка `v.line` не находится внутри блока комментария (по расширению файла) и не является строковым литералом (эвристика: строка не начинается с `#`, `//`, `/*`, `*`, `--`, `"""`, `'''`). | средний | средний (если инвариант намеренно проверяет комментарии — редкий случай, но возможен) |
| **C: Дублирование** | Добавить дедупликацию: группировать находки по `(invariant_id, file_path, line)` и оставлять только первую. | средний | низкий (TP на одной строке с разными инвариантами не теряются — ключ включает `invariant_id`) |
| **D: Мягкая семантика** | Добавить фильтр `_is_high_confidence_invariant(v)`: пропускать находку, если `v.severity == "info"` и `v.invariant_type` не входит в whitelist строгих типов (например, `sql_injection`, `command_injection`, `hardcoded_secret`). | высокий | средний (могут потеряться TP с severity=info, но они обычно не критичны) |

**Примеры кода фильтров (по образцу существующих `_is_placeholder`):**

```python
def _is_applicable_language(self, v, language):
    """Проверяет, применим ли инвариант к языку файла."""
    langs = getattr(v, "languages", None)
    if not langs:
        return True  # нет ограничений — пропускаем
    return language in langs or "*" in langs

def _is_in_active_code(self, content, line_no):
    """Эвристика: строка не в комментарии и не в строковом литерале."""
    lines = content.splitlines()
    if line_no > len(lines):
        return True
    line = lines[line_no - 1].strip()
    # Простейшая проверка: строка не начинается с маркеров комментариев
    comment_markers = ("#", "//", "/*", "*", "--", "\"\"\"", "'''")
    return not line.startswith(comment_markers)

def _deduplicate(self, findings):
    """Оставляет первую находку на (invariant_id, file, line)."""
    seen = set()
    unique = []
    for f in findings:
        key = (f["metadata"]["invariant_id"], f["file"], f["line"])
        if key not in seen:
            seen.add(key)
            unique.append(f)
    return unique

def _is_high_confidence_invariant(self, v):
    """Отсекает 'мягкие' инварианты с severity=info вне whitelist."""
    if v.severity != "info":
        return True
    strict_types = {"sql_injection", "command_injection", "hardcoded_secret"}
    return v.invariant_type in strict_types
```

**Интеграция в `detect()`:**

```python
def detect(self, file_path: str, content: str, language: str = "auto"):
    findings = []
    for v in self.engine.verify_file(file_path, content):
        # Фикс A: языковая применимость
        if not self._is_applicable_language(v, language):
            continue
        # Фикс B: активный код
        if not self._is_in_active_code(content, v.line):
            continue
        # Фикс D: строгие инварианты
        if not self._is_high_confidence_invariant(v):
            continue
        findings.append({...})
    # Фикс C: дедупликация
    return self._deduplicate(findings)
```

## 4. Требует pro-проверки

1. **Структура `InvariantEngine.verify_file()`** — какие поля есть у объекта `v`? Есть ли `languages`, `invariant_type`, `severity`? Без этого фиксы A и D могут быть нереализуемы.
2. **Семантика `severity`** — какие значения используются? Если `severity` всегда `"high"`, фикс D бесполезен.
3. **Поведение движка на комментариях** — действительно ли движок проверяет закомментированный код? Если да, фикс B критичен; если нет — он избыточен.
4. **Частота дублей** — есть ли реальные случаи, когда один инвариант срабатывает несколько раз на одной строке? Если нет, фикс C не нужен.
5. **Конфигурация `.gsc-audit.yml`** — какие инварианты реально используются в репозиториях? Это определит, какие группы FP доминируют.

## 5. Рекомендуемая последовательность

1. **Сначала — pro-проверка** (пункт 4): получить реальные примеры находок GS028 из продакшена. Без них фиксы — гадание.
2. **Фикс C (дедупликация)** — самый безопасный, не влияет на TPR, снижает шум. Внедрить первым.
3. **Фикс A (языковая применимость)** — если подтвердится, что движок возвращает `languages`. Внедрить вторым.
4. **Фикс B (активный код)** — внедрить после анализа реальных FP: если движок уже игнорирует комментарии, фикс не нужен.
5. **Фикс D (строгие инварианты)** — внедрять последним, только если есть статистика, что `severity=info` даёт много FP. Риск потери TP выше.

**Важно:** все фиксы должны быть покрыты юнит-тестами на синтетических примерах (FP и TP), чтобы контролировать падение TPR ≤ 3%.
