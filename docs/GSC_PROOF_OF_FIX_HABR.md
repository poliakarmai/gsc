# Proof-of-Fix: от «нашли уязвимость» к «доказали, что исправили»

> **KDPV (обложка):** сюда вставить картинку-схему контура PoF — цепочка
> `уязвимый код → PoC → песочница → исправленный код → вердикт verified/не verified`.
> Идеально — чистая ASCII-диаграмма на тёмном фоне или минималистичная блок-схема.
> (Сгенерировать схему можно из ASCII-блоков ниже в §«Поток данных».)

*Лид.*

Любой, кто внедрял SAST в CI, знает это чувство: сканер нашёл 300 «критических»
находок, половина — ложные срабатывания, а у оставшихся половины ты вручную
правишь код и **веришь**, что закрыл уязвимость. Не знаешь — именно веришь.
Потому что классический SAST умеет находить, но не умеет доказывать, что фикс
сработал.

Мы сделали иначе. В этой статье — архитектура **Proof-of-Fix**: механизма,
который для каждой находки генерирует эксплойт, генерирует патч и **исполняет
эксплойт против обеих версий кода в песочнице**, прежде чем сказать «исправлено».

---

## Проблема: «исправлено» ≠ «доказано»

Классический SAST (Semgrep, CodeQL, Bandit) решает задачу *обнаружения*. Дальше —
руками. Остаётся фундаментальный разрыв:

- **Находка может быть ложной** — паттерн совпал, уязвимости нет.
- **Исправление может быть неполным** — закрыли один вектор, остался соседний.
- **«Закрыто» не доказано** — статус в трекере не равен отсутствию эксплуатации.

Итог — дорогой ручной триаж, гора непроверенных находок и усталость от алертов.

## Почему конкуренты останавливаются на «предположении»

**Snyk CodeFix** генерирует исправление как diff, но **не проверяет, что diff
действительно устраняет уязвимость**. Для SQL-injection он предложит
параметризованный запрос — но если `user_id` всё ещё приходит из непроверенного
источника и не проходит taint-трекинг до конца, фикс неполный. CodeFix не
исполняет код, чтобы это обнаружить.

**Veracode Fix** делает точечные замены (`eval(user_input)` →
`JSON.parse(user_input)`), но **не проверяет постфактум**, что `user_input` теперь
валиден и не несёт эксплуатируемых конструкций (вложенный SSRF, ReDoS в парсере).

Ключевой вывод:

> Генерация патча — это **предположение**. Верификация через повторный PoC — это
> **факт**. Proof-of-Fix переходит от предположения к факту.

## Proof-of-Fix как архитектурный контракт

Надёжность механизма определяется не набором модулей, а **тремя контрактами**.

**1. Контракт маркеров.** PoC обязан *доказать* эксплуатацию, напечатав один из
маркеров: `VULNERABLE | EXPLOITED | PWNED | LEAKED | SUCCESS | BREACH`. Успех
фиксируется **только** при `exit_code == 0` **и** наличии маркера в stdout. Один
нулевой код возврата не считается — иначе PoC, «просто завершившийся без ошибок»,
был бы ошибочно признан эксплуатирующим.

**2. Контракт изоляции.** Каждое исполнение PoC — в песочнице с лимитами ресурсов
и сети (`RLIMIT_CPU`, `RLIMIT_AS`, `--network none`, `--read-only`, сброс всех
capabilities). PoC не может прочитать секреты хоста, исчерпать ресурсы CI или
скомпрометировать окружение.

**3. Контракт верификации.** Фикс признаётся успешным **только** при строгом
совпадении:

```
poc_before_success == True   И   poc_after_success == False
```

Любое отклонение — фикс неполный или находка ложная — делает результат
непроверенным. Три контракта сводятся к одной формуле:

```
PoF_verified = (poc_before_success == True)
             ∧ (poc_after_success == False)
             ∧ is_container_isolation(before)
             ∧ is_container_isolation(after)
```

Третий и четвёртый конъюнкты — это **fail-closed gate**: вердикт `verified`
допустим только когда обе стадии выполнены в OS-изолированном контейнере. Отсюда
главная гарантия:

> Если PoF говорит `verified` — уязвимость была воспроизведена и устранена в
> контролируемой среде, и никакой сторонний код не мог повлиять на результат.

## Поток данных

```
finding + source
      │
      ▼
[Генерация PoC] ──► poc_code          (детерминированный или LLM)
      │
      ▼
[Генерация патча] ──► patch, до 3 итераций
      │
      ▼
[Песочница]  PoC vs УЯЗВИМЫЙ код ──► poc_before_success
             PoC vs ИСПРАВЛЕННЫЙ код ──► poc_after_success
      │
      ▼
[Fail-closed gate]  контракт верификации + OS-изоляция
      │
      ▼
FixEvidence: verified | structural | syntax_only | failed
```

## Изоляция исполнения

Исполнение сгенерированного PoC — критическая граница: PoC по определению
вредоносный код. Два уровня изоляции:

**Контейнер (основной путь).** Одноразовый Docker/Podman с жёсткими флагами:

| Флаг | Гарантия |
|---|---|
| `--network none` | PoC не может выйти в сеть |
| `--read-only` | корневая ФС неизменяема |
| `--cap-drop ALL` + `--security-opt no-new-privileges` | нет привилегий ядра |
| `--pids-limit 64` / `--memory 512m` / `--cpus 1` | нет fork-бомбы и выжигания ресурсов |
| `--user 65534:65534` | нет root внутри |
| `--tmpfs /tmp` + mount workdir | запись только в свой каталог |

**rlimit fallback (деградация).** Без контейнера — subprocess с POSIX `rlimit`
(`RLIMIT_CPU` 30 с, `RLIMIT_AS` 512 MB, `RLIMIT_NPROC` 64, `RLIMIT_FSIZE` 16 MB,
`RLIMIT_NOFILE` 256). Важно: rlimit — *деградация*, а не изоляция; на fail-closed
gate результат в rlimit-режиме **никогда** не помечается `verified`.

**Изоляция окружения.** PoC получает белый список из 9 переменных окружения
вместо полного `os.environ` — это закрывает утечку секретов хоста
(`DEEPSEEK_API_KEY`, `GITHUB_TOKEN`, `JWT_SECRET`) в исполняемый код.

## Уровни доверия

| Уровень | Критерий | Значение |
|---|---|---|
| `verified` | PoC сработал до фикса, не сработал после, обе стадии в контейнере | доказано |
| `structural` | детектор перестал срабатывать на исправленном коде | косвенно |
| `syntax_only` | синтаксис цел, доказательств нет | слабо |
| `failed` | не удалось сгенерировать/применить/проверить | нет |

## Что это даёт на практике

- **Снижение false-negative в remediation.** Фикс либо доказан эксплуатацией,
  либо честно помечен «не проверено» — «тихо сломанного» закрытия больше нет.
- **Автоматизация цикла.** `finding → proof → fix → verify` без ручного триажа.
- **Сокращение времени** от обнаружения до доказанного закрытия.

## Ограничения (честно)

1. Sandbox исполняет только Python-PoC; JS/Go/Rust — в дорожной карте.
2. Без docker/podman верхний уровень `verified` недостижим — осознанный
   fail-closed выбор.
3. Без LLM-ключа PoC/патч генерируются только для шаблонных классов уязвимостей.
4. PoF оперирует отдельным файлом, а не целым репозиторием.

## Что дальше

- **Runtime Validator (IAST-lite):** верификация по факту runtime-эксплуатации
  (monkeypatch системных вызовов в sandbox-venv, затем `strace`) вместо
  stdout-маркера. Без `--privileged` — он превращает защиту в вектор атаки.
- Поддержка JS/Go/Rust.
- PostgreSQL + RLS для multi-tenant SaaS.

## Заключение

Proof-of-Fix превращает SAST из «детектора» в «машину доказанной реабилитации».
Ключевая идея — **fail-closed**: система скорее откажется подтвердить исправление,
чем выдаст необоснованный `verified`. Это доверие, основанное на доказательствах,
а не на декларациях.
