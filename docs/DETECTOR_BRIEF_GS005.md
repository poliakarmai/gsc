# DETECTOR BRIEF — GS005

## 1. Состояние

Детектор GS005 показывает значительный уровень false-positive (FP) срабатываний, особенно на Python-паттернах f-string инъекций. Основные проблемы:

- **Массовые FP на f-string паттернах**: 17+ FP против 6 TP — соотношение ~3:1 в пользу ложных срабатываний.
- **FP на dict unpacking**: 3 FP против 0 TP — паттерн `GS005-GEN-PY-011` практически полностью ложный.
- **Отсутствие контекстного анализа**: детектор не проверяет, является ли f-string реально SQL-запросом, а не просто вызовом `execute()` с форматированной строкой (например, логирование, сообщения об ошибках).

---

## 2. FP root-cause (по группам)

### Группа A: f-string в `execute()` без SQL-контекста
**Паттерн**: `(?:execute|cursor\.execute|conn\.execute)\s*\(\s*f["\']`  
**FP-примеры**: все `/tmp/tmp*/test.py:1`, `web-lgsm.py:467`, `web-lgsm.py:575`, `update.py:75`, `update.py:230`, `manage_cron.py:108`, `game_server_delete.py:38/77/79`, `edit_users.py:92/93/247/259`, `install.py:54`

**Root-cause**: Паттерн срабатывает на ЛЮБОЙ f-string внутри `execute()`, даже если строка не содержит SQL-ключевых слов (SELECT, INSERT, UPDATE, DELETE и т.д.). Например:
```python
execute(f"User {username} logged in")  # FP — это логирование, не SQL
execute(f"Error: {e}")                 # FP — это сообщение об ошибке
```

**Ключевая проблема**: Существующий фильтр `if not needs_context and len(_SQL_KEYWORDS.findall(line)) == 0` проверяет SQL-ключевые слова только на **всей строке**, но не на **самой f-string**. Если в строке есть `execute(f"...")` и рядом (в той же строке) есть слово `SELECT` в другом контексте — фильтр пропускает.

### Группа B: dict unpacking в `execute()`
**Паттерн**: `\.execute\s*\(\s*.*\w+\s*\[\s*[\"\']\w+[\"\']\s*\].*\)`  
**FP-примеры**: `server_list_order.py:28` (`.execute(item['id'])`), `add.py:98` (`.execute(server['id'])`), `add.py:172` (`.execute(current_user.id, f"User '{current_user.username}', added game server '{server['i...`)  

**Root-cause**: Паттерн слишком широкий — срабатывает на ЛЮБОЙ вызов `.execute()` с dict-индексацией, даже если это:
- Передача параметров в параметризованный запрос (`.execute(item['id'])` — это параметр, а не SQL-строка).
- Вызов метода с именем `execute`, не связанного с SQL (например, `task.execute(item['id'])`).

### Группа C: f-string в `execute()` с не-SQL содержимым, но с SQL-ключевыми словами в строке
**FP-примеры**: `install.py:54` (помечен как `[no user input — verify]`)

**Root-cause**: Строка содержит SQL-ключевые слова (например, `SELECT` в комментарии или в другом контексте), но f-string не является SQL-запросом. Существующий фильтр `_SQL_KEYWORDS` проверяет всю строку, а не только f-string.

## 3. Precision-фиксы

| # | Root-cause | Фикс | FP-срез | TP-риск |
|---|-----------|------|---------|---------|
| 1 | **Группа A**: f-string без SQL-ключевых слов внутри самой f-string | **Добавить фильтр**: проверить, что f-string содержит SQL-ключевые слова. Реализация: после матча паттерна, извлечь f-string из `matched` и проверить `_SQL_KEYWORDS.search(f_string_content)`. Если нет — пропустить. **[flash-гипотеза]** | **Высокий** (убирает ~80% FP из группы A) | **Низкий** (TP всегда содержат SQL-ключевые слова в f-string) |
| 2 | **Группа A**: f-string с SQL-ключевыми словами, но это не запрос (логирование, сообщения) | **Добавить фильтр**: проверить, что f-string начинается с SQL-ключевого слова (SELECT/INSERT/UPDATE/DELETE/DROP/CREATE/ALTER). Реализация: `_SQL_START = re.compile(r'^\s*(?:SELECT|INSERT|UPDATE|DELETE|DROP|CREATE|ALTER)\b', re.IGNORECASE)` — проверять на извлечённой f-string. **[flash-гипотеза]** | **Средний** (убирает FP где f-string = "User X logged in" но строка содержит SELECT в другом месте) | **Низкий** (реальные SQL-запросы начинаются с SQL-ключевого слова) |
| 3 | **Группа B**: dict unpacking без SQL-контекста | **Уточнить паттерн**: добавить требование наличия SQL-ключевых слов в строке. Заменить `\.execute\s*\(\s*.*\w+\s*\[\s*[\"\']\w+[\"\']\s*\].*\)` на `\.execute\s*\(\s*.*\w+\s*\[\s*[\"\']\w+[\"\']\s*\].*\)` + фильтр `_SQL_KEYWORDS.search(line)` (уже есть, но добавить в `_INTERPOLATION_REQUIRED`). **[flash-гипотеза]** | **Высокий** (убирает все 3 FP из группы B) | **Низкий** (TP с dict unpacking всегда содержат SQL-ключевые слова) |
| 4 | **Группа A**: f-string в `execute()` — добавить проверку на параметризованные запросы | **Добавить фильтр**: если строка содержит `?` или `%s` и f-string используется как параметр (не как SQL), пропустить. Реализация: если `re.search(r'(\?|%s)', line)` и f-string не содержит SQL-ключевых слов — пропустить. **[flash-гипотеза]** | **Средний** (убирает FP где f-string = "SELECT * FROM users WHERE id = ?" — это параметризованный запрос) | **Низкий** (TP с параметризацией всё равно содержат SQL-ключевые слова) |
| 5 | **Группа A**: f-string в `execute()` — добавить проверку на `execute()` с несколькими аргументами | **Добавить фильтр**: если `execute()` вызывается с несколькими аргументами (например, `execute(f"...", params)`), это параметризованный запрос — пропустить. Реализация: проверить, что после f-string есть запятая и ещё аргументы. **[flash-гипотеза]** | **Средний** (убирает FP типа `execute(f"SELECT...", (user_id,))`) | **Низкий** (TP с параметризацией — это не инъекция) |
| 6 | **Группа C**: f-string с SQL-ключевыми словами, но не начинается с них | **Добавить фильтр**: проверить, что f-string начинается с SQL-ключевого слова (см. фикс #2). **[flash-гипотеза]** | **Средний** (убирает FP где f-string = "Error: SELECT failed") | **Низкий** (реальные SQL-запросы начинаются с SQL-ключевого слова) |

## 4. Требует pro-проверки

1. **Фикс #1 (SQL-ключевые слова в f-string)**: Нужно проверить, что все TP-примеры (`app.py:21`, `app.py:23`, `app.py:44`) содержат SQL-ключевые слова **внутри** f-string. Если есть TP, где f-string не содержит SQL-ключевых слов (например, `execute(f"SELECT * FROM {table}")` — содержит, но `execute(f"User {name}")` — нет), фикс может отсечь TP.

2. **Фикс #2 (f-string начинается с SQL-ключевого слова)**: Нужно проверить, что в TP-примерах f-string действительно начинается с SQL-ключевого слова. Если есть TP вида `execute(f"SELECT * FROM {table} WHERE id = {id}")` — начинается с SELECT, ок. Но если есть `execute(f"WHERE id = {id}")` — не начинается, фикс отсечёт TP.

3. **Фикс #3 (dict unpacking)**: Нужно проверить, есть ли TP-примеры с dict unpacking, где SQL-ключевые слова отсутствуют в строке. Если есть — фикс отсечёт TP.

4. **Фикс #5 (множественные аргументы)**: Нужно проверить, есть ли TP-примеры, где `execute()` вызывается с несколькими аргументами и при этом уязвим. Например, `execute(f"SELECT * FROM {table}", (user_id,))` — если `table` из пользовательского ввода, это уязвимо, но фикс отсечёт.

---

## 5. Рекомендуемая последовательность

1. **Сначала фикс #1** (SQL-ключевые слова в f-string) — самый большой FP-срез, минимальный TP-риск.
2. **Затем фикс #3** (dict unpacking) — полностью устраняет группу B, TP-риск низкий.
3. **Потом фикс #2** (f-string начинается с SQL-ключевого слова) — дополнительно снижает FP, но требует pro-проверки.
4. **В конце фиксы #4, #5, #6** — точечные, требуют pro-проверки перед применением.

**Важно**: Перед применением фиксов #1 и #2 необходимо проверить TP-примеры на соответствие условиям (содержат ли SQL-ключевые слова в f-string, начинается ли f-string с SQL-ключевого слова). Если TP не соответствуют — фиксы нужно скорректировать.
