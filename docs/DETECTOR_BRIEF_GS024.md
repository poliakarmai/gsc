# DETECTOR BRIEF — GS024

## 1. Состояние

Детектор GS024 — LLM-based SQL injection детектор. Архитектура: grep-префильтр → извлечение кандидатов → LLM-классификация. 

**Ключевая проблема**: детектор генерирует **дублирующиеся находки** — в выборке непроверенных находок один и тот же файл/строка (`app.py:21`, `app.py:44`) повторяется 5-6 раз. Это указывает на то, что либо детектор вызывается многократно на одном и том же файле, либо `_extract_candidates` извлекает несколько кандидатов с одной и той же строки.

**Второстепенная проблема**: LLM-промпт не содержит явных инструкций по работе с **второстепенными (second-order) SQL-инъекциями** — в TP-примерах видно, что LLM корректно определяет их, но это происходит скорее случайно, чем системно.

**Третья проблема**: отсутствие дедупликации находок по `(file_path, line_number)` — это прямое следствие первой проблемы.

---

## 2. FP root-cause (по группам)

### Группа A: Дублирование находок (не FP в классическом смысле, но шум)
- **Root-cause**: `_extract_candidates` извлекает до 3 кандидатов на файл, но если в файле несколько строк, содержащих `execute(` с f-string, каждый кандидат отправляется в LLM. При этом LLM может вернуть `vulnerable=true` для нескольких кандидатов, указывающих на **одну и ту же уязвимость** (например, строка с вызовом `execute` и строка с формированием SQL-запроса).
- **Дополнительно**: отсутствует дедупликация по `(file_path, line_number)` перед добавлением в findings.

### Группа B: Ложные срабатывания на безопасные f-string с внутренними переменными
- **Root-cause**: `_extract_candidates` срабатывает на **любой** f-string внутри `execute()`/`query()`, включая случаи, где интерполируются только внутренние константы или переменные, не связанные с пользовательским вводом. LLM-промпт содержит инструкцию "f-strings with trusted/internal variables only" как SAFE, но **не даёт LLM инструментов для определения "trusted"** — он должен догадываться по контексту.
- **Пример**: `cursor.execute(f"SELECT * FROM config WHERE key = '{DEFAULT_KEY}'")` — LLM может посчитать это уязвимым, если не увидит, что `DEFAULT_KEY` — константа.

### Группа C: Срабатывание на ORM-паттерны с f-string
- **Root-cause**: `PRE_FILTER_PATTERNS` включает `find_by_sql`, `$where`, `$regex` — это паттерны, которые могут встречаться в безопасном ORM-коде (например, `Model.objects.filter(name__regex=r"^[a-z]+$")`). LLM-промпт упоминает Django ORM как SAFE, но **не упоминает** `find_by_sql` с параметрами или `$regex` в MongoDB как потенциально безопасные.

### Группа D: Срабатывание на тестовые фикстуры и документацию
- **Root-cause**: `_extract_candidates` не фильтрует файлы по пути (например, `test_*.py`, `tests/`, `fixtures/`, `docs/`). LLM-промпт упоминает "Test fixtures, documentation examples" как SAFE, но **не гарантирует**, что LLM это учтёт, особенно если контекст неоднозначен.

Дополнительно: если две строки в пределах 3 строк друг от друга содержат одинаковый SQL-паттерн, брать только первую. **[flash-гипотеза]** | **Средний** (уменьшает количество LLM-вызовов и дублей) | **Низкий** (TP-строки уникальны) |

## 4. Требует pro-проверки

1. **Фикс #3 (константы)**: Необходимо проверить на корпусе, как часто константы в f-string реально переопределяются из user input. Если это происходит часто, фикс может пропустить TP.

2. **Фикс #7 (источник данных)**: Порог в 20 строк контекста может быть недостаточным — user input может приходить через глобальные переменные, импорты или функции, определённые выше. Требуется анализ корпуса на предмет TP, где источник данных не виден в 20 строках.

3. **Фикс #5 (тестовые файлы)**: Нужно проверить, есть ли в корпусе TP в тестовых файлах (например, тесты, демонстрирующие уязвимость). Если есть — фикс нужно смягчить (например, пропускать только `test_*.py`, но не `tests/`).

4. **Фикс #4 (ORM)**: Паттерн `$regex` в MongoDB может быть уязвим, если значение интерполируется из user input. Фикс должен отличать `$regex` с константой от `$regex` с переменной.

5. **Общая проблема дублирования**: Необходимо проверить, вызывается ли `detect()` многократно на одном и том же файле (например, из-за нескольких вызовов из orchestrator). Если да — дедупликация в `detect()` не решит проблему полностью, нужна дедупликация на уровне orchestrator.

## 5. Рекомендуемая последовательность

**Шаг 1 (критический, немедленно)**: Фикс #1 — дедупликация находок по `(file_path, line_number)`. Это устранит ~80% шума в текущей выборке без какого-либо риска для TP.

**Шаг 2 (быстрый выигрыш)**: Фикс #2 — дедупликация кандидатов в `_extract_candidates`. Уменьшит количество LLM-вызовов и ускорит сканирование.

**Шаг 3 (precision-буст)**: Фикс #7 — фильтр `_has_user_input_source`. Это самый сильный precision-фикс, но требует pro-проверки на корпусе.

**Шаг 4 (точечные фильтры)**: Фиксы #3, #4, #5 — добавить после проверки фикса #7, чтобы не пересекаться по эффекту.

**Шаг 5 (промпт-инжиниринг)**: Фикс #6 — улучшение LLM-промпта. Делать после всех фильтров, чтобы оценить эффект изолированно.

**Важно**: После каждого шага — прогон на корпусе TP/FP, контроль TPR (допустимое падение ≤ 3%).
