# DETECTOR BRIEF — GS037

## 1. Состояние

Детектор GS037 содержит 25 regex-паттернов для Python-кода. Основная проблема — **паттерн `pickle_load_any`** с confidence 0.70, который срабатывает на **любой** вызов `pickle.loads()`/`pickle.load()` без проверки источника данных. Это даёт массовые FP на тестовых файлах вида:

```python
def load(x):
    return pickle.loads(x)
```

Такие файлы — это **обёртки/функции-прокси**, где `pickle.loads()` вызывается с параметром функции, а не с внешним пользовательским вводом. Паттерн `pickle_rce` (более строгий) корректно ловит TP с `request.*`/`input`, но `pickle_load_any` дублирует его и добавляет шум.

Дополнительно: паттерн `pickle_load_any` не исключает уже покрытые `pickle_rce` случаи, что приводит к **дублированию находок** на одном и том же коде.

---

## 2. FP root-cause (по группам)

### Группа A: «Функция-обёртка» (основная, ~90% FP)
Файлы вида:
```python
def load(x):
    return pickle.loads(x)
```
Паттерн `pickle_load_any` матчит `pickle.loads(x)` без проверки, что `x` — это параметр функции (не внешний ввод). В тестовых корпусах такие обёртки — стандартный паттерн для unit-тестов.

### Группа B: «Дублирование с pickle_rce»
Когда код содержит `pickle.loads(request.data)`, срабатывают **оба** паттерна: `pickle_rce` (0.98) и `pickle_load_any` (0.70). Это создаёт две находки на одно место — шум в отчёте.

### Группа C: «Ложное срабатывание на имя функции load»
Паттерн `pickle_load_any` матчит `pickle.loads` внутри функции с именем `load`. В тестовых корпусах это часто просто имя функции, не связанное с реальной уязвимостью.

## 4. Требует pro-проверки

1. **Фикс 1/3**: Нужна pro-проверка на реальных TP — не маскирует ли фильтр `_is_parameter_passed` случаи, где параметр функции действительно приходит из пользовательского ввода (например, `def process(data): return pickle.loads(data)` в реальном приложении, где `data` — из HTTP). **Риск: средний** — если такие TP есть, фильтр их потеряет.

2. **Фикс 2**: Проверить, что пропуск `pickle_load_any` при наличии `pickle_rce` не теряет TP в случаях, где `pickle_rce` не сработал (например, `pickle.loads(base64.b64decode(data))` — `pickle_rce` не матчит, а `pickle_load_any` должен сработать). **Риск: низкий** — но нужно убедиться, что логика не блокирует `pickle_load_any` для других строк.

3. **Фикс 4**: Проверить, что исключение имени функции `load` не пропустит TP вида `def load(request): return pickle.loads(request.data)` — здесь имя функции `load`, но аргумент — `request`. **Риск: средний** — нужно проверять не имя функции, а источник аргумента.

4. **Общее**: Проверить, что AST-подход (если будет использован) не ломается на синтаксически некорректном коде (файлы с ошибками парсинга).

---

## 5. Рекомендуемая последовательность

1. **Сначала Фикс 2** (дедупликация) — самый безопасный, нулевой TP-риск, убирает дубли.
2. **Затем Фикс 1+3** (фильтр обёрток) — основной FP-срез, но требует pro-проверки на TP.
3. **Потом Фикс 4** (имя функции) — только после проверки, что не маскирует TP с `request` в аргументе.
4. **В конце Фикс 5** (снижение confidence) — как дополнительная страховка, если FP остаются.

**Итоговая оценка**: Фиксы 1-3 должны убрать ~95% FP из тестовых корпусов (все `def load(x): return pickle.loads(x)`), сохраняя TP вида `pickle.loads(base64.b64decode(data))` и `pickle.loads(request.data)`. Падение TPR ≤ 1% (только если в реальных приложениях есть обёртки с пользовательским вводом — что маловероятно).
