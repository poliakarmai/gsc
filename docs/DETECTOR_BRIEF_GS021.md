# DETECTOR BRIEF — GS021

## 1. Состояние

Детектор GS021 показывает **критический уровень шума** на двух паттернах:

- `SSRF candidate: reference to localhost` — **~80% всех FP**. Паттерн `localhost|127\.0\.0\.1|0\.0\.0\.0` срабатывает на любом упоминании этих строк в коде: конфигурация серверов, дефолтные значения, документация, SQL-строки, комментарии.
- `Potential CSRF: POST route without token check` — **~20% FP**. Паттерн `@app\.route.*methods\s*=\s*\[.*POST` срабатывает на любой POST-маршрут без проверки контекста (наличие CSRF-токена, декораторов защиты, использования Flask-WTF и т.д.).

Остальные паттерны (AWS metadata, Docker socket, `file_get_contents`, `curl_exec`) работают приемлемо — FP по ним не зафиксированы.

**Ключевая проблема**: паттерн `localhost` — это **INFO-уровень**, но он генерирует шум, который полностью забивает реальные находки. Паттерн POST-маршрутов — **MEDIUM**, но без контекстного анализа он бесполезен.

---

## 2. FP root-cause (по группам)

### Группа A: `localhost` в конфигурации сервера (app.run, uvicorn.run)

**Примеры**: `app.run(host="127.0.0.1", port=...)`, `uvicorn.run(app, host="127.0.0.1", port=...)`

**Root-cause**: Паттерн `localhost|127\.0\.0\.1|0\.0\.0\.0` не различает **bind-адрес сервера** (легитимная конфигурация) и **URL для HTTP-запроса** (потенциальный SSRF). `app.run(host="127.0.0.1")` — это стандартный способ запуска Flask-приложения локально, а не SSRF-вектор.

### Группа B: `localhost` в дефолтных значениях конфигурации

**Примеры**: `POSTGRES_HOST: str = Field(default="localhost")`, `WEB_SERVER_HOST: str = Field(default="0.0.0.0")`, `"127.0.0.1"` в списке разрешённых хостов

**Root-cause**: Паттерн срабатывает на **строковые литералы** в конфигурационных структурах (Pydantic Field, списки, словари). Это не URL-запросы, а данные конфигурации.

### Группа C: `localhost` в строках документации/комментариев/SQL

**Примеры**: `--source-dsn postgresql://user:pass@localhost:5432/remnashop`, `const baseURL = \`http://127.0.0.1:${PORT}\``

**Root-cause**: Паттерн не различает **контекст использования**: SQL-строка, URL для фронтенда, документация — всё это не является SSRF-вектором, но паттерн срабатывает.

### Группа D: `localhost` как дефолтное значение переменной

**Примеры**: `host = request.args.get("host", "127.0.0.1")`, `self.default_client_ip = "127.0.0.1"`

**Root-cause**: Паттерн срабатывает на **дефолтные значения** — это не значит, что переменная будет использована для HTTP-запроса. В первом случае — это fallback для параметра запроса, во втором — атрибут класса.

### Группа E: POST-маршруты без контекста CSRF-защиты

**Примеры**: `@app.route("/register", methods=["POST"])`, `@app.route("/load", methods=["POST"])`

**Root-cause**: Паттерн `@app\.route.*methods\s*=\s*\[.*POST` срабатывает на **любой POST-маршрут**, не проверяя: есть ли в функции CSRF-токен, используется ли Flask-WTF (который автоматически защищает), есть ли декоратор `@csrf_protect` и т.д. Это даёт огромный FP на легитимных маршрутах.

### Группа F: f-string URL без проверки источника переменной

**Примеры**: `f"https://{raw}"` — где `raw` — это строка, переданная из конфигурации, а не из пользовательского ввода

**Root-cause**: Паттерн `f[\"\']https?://\{` срабатывает на **любую f-string с URL**, не проверяя, откуда берётся переменная. Если `raw` — это константа или значение из конфигурации, это не SSRF.

## 3. Precision-фиксы

| # | Root-cause | Фикс | FP-срез | TP-риск |
|---|-----------|------|---------|---------|
| 1 | **A**: `localhost` в bind-адресе сервера | Добавить фильтр `_is_server_bind(snippet)`: если строка содержит `app.run(` или `uvicorn.run(` и `host=` — пропустить. **Альтернатива**: сузить regex до `(?:requests|urllib|httpx|axios|fetch|got)\.(?:get|post|request|fetch)\s*\(.*(?:localhost|127\.0\.0\.1|0\.0\.0\.0)` — только URL-запросы к localhost | **Высокий** (~40% всех FP) | **Низкий** — bind-адрес не является SSRF-вектором |
| 2 | **B**: `localhost` в дефолтных значениях конфигурации | Добавить фильтр `_is_config_default(snippet)`: если строка содержит `Field(default=`, `default=`, `os.environ.get(`, `getenv(` — пропустить | **Высокий** (~20% FP) | **Низкий** — конфигурационные дефолты не являются SSRF |
| 3 | **C**: `localhost` в SQL/документации/фронтенд-URL | Добавить фильтр `_is_non_http_context(snippet)`: если строка содержит `postgresql://`, `mysql://`, `mongodb://`, `baseURL`, `const` (JS-константа) — пропустить | **Средний** (~10% FP) | **Низкий** — SQL-строки и фронтенд-константы не являются SSRF |
| 4 | **D**: `localhost` как дефолт переменной | Добавить фильтр `_is_default_value(snippet)`: если строка содержит `request.args.get(`, `request.form.get(`, `self.` + `= "` — пропустить | **Средний** (~10% FP) | **Низкий** — дефолтные значения не означают использование для HTTP-запроса |
| 5 | **E**: POST-маршруты без контекста | **Заменить паттерн** `@app\.route.*methods\s*=\s*\[.*POST` на два: (1) `@app\.route.*methods\s*=\s*\[.*POST` **+ фильтр** `_has_csrf_protection(content, line_no)`: проверить 10 строк ниже — есть ли `csrf_token`, `@csrf_protect`, `CSRFProtect`, `WTF_CSRF_ENABLED`; (2) новый паттерн `@app\.route.*methods\s*=\s*\[.*POST.*\]` + проверка, что в функции **нет** `@login_required` и `@admin_required` (эти декораторы часто подразумевают CSRF-защиту на уровне фреймворка) | **Высокий** (~20% FP) | **Средний** — есть риск пропустить реальный CSRF, если защита реализована нестандартно |
| 6 | **F**: f-string URL с константой | Добавить фильтр `_is_constant_source(snippet, content, line_no)`: если переменная в f-string определена выше как константа (строка с `=` и литералом) — пропустить. **Альтернатива**: сузить regex до `f[\"\']https?://\{.*(?:request\.|params\[|req\.(?:query|body|params)|user_input|input\()` — только f-string с user-tainted переменными | **Средний** (~5% FP) | **Средний** — риск пропустить SSRF, если переменная переопределяется позже |
| 7 | **Все группы A-D**: `localhost` INFO-паттерн | **Снизить severity до INFO** (уже INFO) и **добавить фильтр `_is_http_request_context(snippet)`**: срабатывать только если строка содержит HTTP-клиент (`requests.`, `urllib.`, `httpx.`, `axios.`, `fetch(`, `got(`, `curl_`) | **Высокий** (~80% всех FP на localhost) | **Низкий** — SSRF без HTTP-клиента невозможен |

## 4. Требует pro-проверки

1. **Фикс #5 (POST-маршруты)**: Требует проверки на реальных проектах с Flask-WTF. Если проект использует `CSRFProtect(app)` глобально — все POST-маршруты защищены, и паттерн должен быть полностью отключён. Если нет — фильтр `_has_csrf_protection` может пропустить реальные уязвимости.

2. **Фикс #6 (f-string)**: Требует проверки, как часто переменная в f-string URL переопределяется из user-input после инициализации. Если это распространено — фильтр `_is_constant_source` даст TP-потери.

3. **Фикс #7 (HTTP-контекст)**: Требует проверки, есть ли реальные SSRF-сценарии, где localhost используется **без** HTTP-клиента (например, `socket.connect(("127.0.0.1", port))`). Если такие сценарии есть — фильтр `_is_http_request_context` их пропустит.

4. **Группа C**: Требует проверки, есть ли SSRF-сценарии через SQL-инъекции, где `localhost` в SQL-строке может быть использован для SSRF (например, через `LOAD_FILE` в MySQL). Если да — фильтр `_is_non_http_context` может пропустить реальные уязвимости.

5. **Общий вопрос**: Нужно ли вообще оставлять INFO-паттерн `localhost`? Если он генерирует 80% шума и не даёт TP — возможно, его стоит заменить на более точный паттерн `(?:requests|urllib|httpx|axios|fetch|got)\.(?:get|post|request|fetch)\s*\(.*(?:localhost|127\.0\.0\.1|0\.0\.0\.0)`.

---

## 5. Рекомендуемая последовательность

### Шаг 1 (немедленно, максимальный эффект):
Применить **фикс #7** — фильтр `_is_http_request_context` для INFO-паттерна `localhost`. Это уберёт ~80% всех FP без риска для TP (SSRF без HTTP-клиента — крайне редкий сценарий).

### Шаг 2 (сразу после):
Применить **фикс #1** — фильтр `_is_server_bind` для `app.run`/`uvicorn.run`. Это уберёт ещё ~40% от оставшихся FP.

### Шаг 3 (в течение дня):
Применить **фикс #5** — контекстный фильтр для POST-маршрутов. Это уберёт ~20% FP, но требует pro-проверки на реальных проектах.

### Шаг 4 (после анализа):
Применить **фиксы #2, #3, #4** — фильтры для конфигурационных дефолтов, SQL-строк и дефолтных значений переменных.

### Шаг 5 (после pro-проверки):
Применить **фикс #6** — фильтр для f-string с константами.
