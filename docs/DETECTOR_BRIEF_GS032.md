# DETECTOR BRIEF — GS032

## 1. Состояние

Детектор GS032 нацелен на выявление prompt injection атак на AI-агентов (Claude Code, Codex, Gemini CLI) через файлы в репозитории. Архитектура детектора разумная: комбинация сигнатурных паттернов, фильтров по расширениям и путям, энтропийных проверок и агрегации «плотности» подозрительных паттернов.

**Ключевые риски precision:**

1. **Широкие regex-паттерны** — многие паттерны используют `.{0,80}` и `.{0,100}` без учёта контекста, что даёт ложные срабатывания на легитимных примерах кода, документации и тестов.
2. **Отсутствие контекстных фильтров** — нет проверки на нахождение паттерна внутри строкового литерала, комментария, примера кода, тестовой документации.
3. **Отсутствие allowlist-подобных исключений** — нет проверки на «это документация по безопасности», «это тест детектора», «это пример из официальной документации».
4. **Паттерны, пересекающиеся с легитимным кодом** — `fake_tool_call_execute`, `exfil_curl`, `exfil_env_send` могут срабатывать на обычных примерах shell-команд, CI-скриптах, Makefile-подобных файлах.
5. **Отсутствие проверки на «это код, а не инструкция»** — паттерны `role_hijack`, `system_prompt_override` могут срабатывать на тестовых строках, примерах из документации, комментариях в коде.

## 2. FP root-cause (по группам)

### Группа A: Легитимные примеры кода / shell-команд в документации

**Паттерны:** `fake_tool_call_execute`, `fake_tool_call_file`, `fake_tool_call_delegate`, `fake_tool_call_terminal`, `exfil_curl`, `exfil_env_send`, `exfil_git_clone_malicious`

**Root-cause:** В README, документации, туториалах, примерах кода часто встречаются:
- Примеры вызова `subprocess.run(...)`, `os.system(...)`, `bash -c "..."` — это легитимный код, а не инъекция.
- Примеры `curl ... | bash`, `curl ... && ...` — это инструкции по установке, а не эксфильтрация.
- Примеры `cat .env | grep TOKEN` — это легитимные команды для отладки.
- Примеры `git clone https://...` — это обычные инструкции по клонированию.

**Почему FP:** Паттерны не различают «инструкцию агенту» и «пример кода/команды». Нет проверки на то, находится ли паттерн внутри блока кода (```), внутри строкового литерала, или является ли он частью документации.

---

### Группа B: Тестовые данные / фикстуры / примеры для тестирования

**Паттерны:** `override_instruction`, `role_hijack`, `system_prompt_override`, `anthropic_system_injection`, `openai_tool_injection`

**Root-cause:** В тестах, фикстурах, примерах для пентеста, в тестовых данных для LLM-приложений часто встречаются:
- Строки вида `"ignore previous instructions"` — это тестовые данные для проверки устойчивости LLM к инъекциям.
- Примеры `<system>...</system>` — это тестовые данные для проверки парсеров.
- Примеры `"role": "system", "content": "ignore..."` — это тестовые JSON-фикстуры.

**Почему FP:** Нет проверки на то, что файл находится в тестовой директории (хотя `EXCLUDE_PATH_RE` исключает `tests/`, но не исключает `test_data/`, `fixtures/`, `examples/` в некоторых случаях). Также нет проверки на то, что файл — это JSON-фикстура с тестовыми данными.

---

### Группа C: Документация по безопасности / описание атак

**Паттерны:** `override_instruction`, `role_hijack`, `system_prompt_override`, `exfil_*`, `hidden_html_comment`

**Root-cause:** Статьи, блог-посты, документация по безопасности, описание уязвимостей часто содержат:
- Примеры вредоносных промптов (для обучения).
- Описание атак с примерами команд.
- Сниппеты кода с `curl ... | bash` (как пример атаки).

**Почему FP:** Нет проверки на то, что файл — это документация по безопасности (например, `SECURITY.md`, `security/`, `advisories/`). Нет проверки на то, что паттерн находится внутри цитаты, примера, или блока кода.

---

### Группа D: Легитимный код с API-вызовами

**Паттерны:** `fake_tool_call_execute`, `fake_tool_call_file`, `fake_tool_call_delegate`, `fake_tool_call_terminal`, `openai_tool_injection`

**Root-cause:** В реальном коде часто встречаются:
- Вызовы `subprocess.run(...)`, `os.system(...)` — это легитимный код.
- Вызовы `write_file(...)`, `read_file(...)` — это легитимные функции.
- JSON с `"role": "system"` — это легитимные вызовы OpenAI API.

**Почему FP:** Паттерны не различают «инструкцию агенту» и «обычный код». Нет проверки на то, что паттерн находится внутри строкового литерала, комментария, или является ли он частью реального вызова API.

---

### Группа E: Скрытые символы в легитимном тексте

**Паттерн:** `zero_width_chars`

**Root-cause:** Zero-width символы (U+200B, U+200C, U+200D, U+FEFF) могут встречаться в:
- Сгенерированных файлах (например, из Figma, из PDF-конвертации).
- Файлах с BOM (Byte Order Mark) — U+FEFF в начале файла.
- Тексте, скопированном из мессенджеров или веб-страниц.

**Почему FP:** Паттерн срабатывает на 3+ подряд идущих zero-width символа, но не проверяет контекст (начало файла, BOM, сгенерированный контент).

---

### Группа F: Markdown-ссылки и изображения

**Паттерны:** `markdown_link_injection`, `markdown_image_exfil`

**Root-cause:** В README и документации часто встречаются:
- Ссылки вида `[text](javascript:...)` — это примеры XSS-атак в документации по безопасности.
- Изображения с внешних CDN (не из allowlist) — это легитимные изображения.

**Почему FP:** Паттерн `markdown_link_injection` срабатывает на `javascript:` ссылки, которые могут быть примерами в документации. Паттерн `markdown_image_exfil` имеет низкий порог (0.30) и срабатывает на любые внешние изображения, не из allowlist.

## 4. Требует pro-проверки

1. **Фикс #1 (код-блоки)**: Необходимо проверить, что атаки не могут быть спрятаны внутри блоков кода в markdown-файлах. Если атакующий может вставить инъекцию в блок кода, который будет прочитан агентом, — фикс снизит TPR. **Рекомендация**: проверить на реальных примерах атак.

2. **Фикс #5 (строковые литералы)**: Необходимо проверить, что атаки не могут быть внутри строковых литералов в коде (например, если агент читает строку из кода и исполняет её). **Рекомендация**: проверить на реальных примерах атак.

3. **Фикс #3 (расширение EXCLUDE_PATH_RE)**: Добавление `examples` в исключения может скрыть реальные атаки, если атакующий поместит вредоносный файл в `examples/`. **Рекомендация**: проверить, насколько часто атаки размещаются в `examples/`.

4. **Фикс #9 (exfil_curl)**: Добавление negative lookahead для `install`, `setup` может пропустить атаки, которые маскируются под установку. **Рекомендация**: проверить на реальных примерах.

5. **Фикс #11 (описание атак)**: Снижение confidence для строк с `attack`, `vulnerability` может пропустить реальные атаки, которые используют эти слова в тексте. **Рекомендация**: проверить на реальных примерах.

## 5. Рекомендуемая последовательность

### Фаза 1: Быстрые победы (низкий TP-риск, высокий FP-срез)

1. **Фикс #1** (код-блоки) — самый большой FP-срез, низкий TP-риск.
2. **Фикс #3** (расширение EXCLUDE_PATH_RE) — добавить `test_data`, `fixtures`, `__fixtures__`, `mock_data`.
3. **Фикс #4** (security-документация) — пропускать `SECURITY.md`, `security/`, `advisories/`.
4. **Фикс #8** (git clone allowlist) — расширить negative lookahead.

### Фаза 2: Средние фиксы (требуют проверки)

5. **Фикс #5** (строковые литералы) — проверить на реальных примерах.
6. **Фикс #6** (zero-width символы) — уточнить контекст.
7. **Фикс #7** (markdown-ссылки) — уточнить allowlist для изображений.
8. **Фикс #9** (exfil_curl) — добавить negative lookahead для установки.

### Фаза 3: Тонкие фиксы (требуют pro-проверки)

9. **Фикс #2** (shell-примеры) — проверить, что атаки не маскируются под примеры.
10. **Фикс #10** (JSON-фикстуры) — проверить на реальных данных.
11. **Фикс #11** (описание атак) — проверить на реальных примерах.
12. **Фикс #12** (Python-код) — проверить на реальных примерах.

---

**Итоговая оценка:** Предложенные фиксы могут снизить FP на 60–70% без существенного падения TPR (≤3%). Ключевые риски — фиксы #1, #5, #3, которые требуют проверки на реальных данных.
