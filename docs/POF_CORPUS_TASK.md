## 1. Что такое GSC (краткий контекст)

GSC (Git Security Checker) — самообучающаяся платформа безопасности приложений (SAST).
Репозиторий: `github.com/poliakarmai/gsc`.

Ключевая фича — **Proof-of-Fix (PoF)**: GSC не просто находит уязвимость, а замыкает цикл:
1. **Detect** — 41 детектор находят уязвимость (SQLi, XSS, SSTI, SSRF, command injection…).
2. **Prove** — генератор строит **детерминированный PoC** и запускает его в изолированной
   песочнице (`gsc_pof_sandbox.py`) → уязвимость реально эксплуатируется.
3. **Fix** — генератор создаёт патч.
4. **Verify (PoF)** — патч прогоняется через тот же exploit: если он больше не срабатывает,
   исправление верифицировано.

PoC бывает двух типов: `python` (импорт модуля + вызов) и `curl/bash` (HTTP-запрос к
запущенному web-таргету). Для `curl`-PoC песочница поднимает таргет как HTTP-сервер.

## 2. Проблема (что нужно решить)

Замер PoF на корпусе `benchmark/real_world/` (10 популярных open-source проектов) дал
**0% passed**: 2648 находок → 55 PoC → 0 подтверждённых.

**Root cause (диагностировано, не догадка):** корпус состоит из **библиотек и CLI**,
а не из web-приложений:

| Проект | Тип | Почему PoF не применим |
|---|---|---|
| sanic | web-фреймворк | entrypoint-детект находит `sanic/simple.py` — учебный пример, не приложение |
| fastapi-users | web-фреймворк | entrypoint = `examples/beanie/app.py` — example, не приложение |
| flask-smorest | web-фреймворк | библиотека, нет standalone `app = Flask(...)` |
| rich, httpie, youtube-dl, thefuck, loguru, pendulum | CLI/библиотеки | нет HTTP-таргета вообще |

**Вывод:** PoF-механизм работает (доказано e2e: multi-module Flask app → `VULNERABLE`),
но curl-PoC применим **только к standalone web-приложениям**. Замеряли не тот класс проектов.

## 3. Что нужно (постановка задачи)

Собрать **корпус standalone web-приложений с известными уязвимостями**, на котором можно
честно замерить PoF pass-rate (ненулевой).

### Требования к корпусу

1. **Standalone**: каждое приложение должно реально запускаться (`app = Flask(...)` +
   роуты, `uvicorn`/`app.run()`). Никаких фреймворков-библиотек и CLI.
2. **Известные уязвимости (ground truth)**: для каждого приложения — точное описание,
   какая уязвимость, на каком endpoint, с каким payload. Чтобы можно было сверять «нашёл → подтвердил».
3. **Покрытие классов**: минимум — SQLi, XSS, SSTI, SSRF, command injection, path
   traversal, IDOR/авторизация. Желательно — deserialization, XXE, open redirect.
4. **Пара «уязвимое / исправленное»**: для каждого приложения нужна версия ДО (vulnerable)
   и ПОСЛЕ (patched) — это и есть материал для PoF (exploit должен срабатывать до фикса
   и падать после).
5. **Формат**: каждое приложение в своей директории, минимальные зависимости
   (Flask/FastAPI + нужные), документация в `README.md` (какая vuln, endpoint, payload, как запустить).

### Вопросы, которые нужно проработать (это и есть суть задачи)

1. **Где взять корпус**: писать свои уязвимые demo-apps (наиболее контролируемо), или
   взять готовые (OWASP Juice Shop, vuln-flask-app, DVWA, нарочно уязвимые FastAPI-примеры)?
   Плюсы/минусы каждого.
2. **Структура**: как организовать `benchmark/pof_corpus/` — поддиректории по классу vuln,
   по фреймворку, или единый формат `app/{vulnerable,patched}/`?
3. **Как хранить patched-версию**: отдельный файл, git-теги, или патч-файл (`fix.patch`)?
4. **Как автоматизировать замер**: скрипт, который для каждого приложения запускает
   GSC scan → PoC → verify, и выдаёт таблицу pass-rate по классам.
5. **Метрика**: что считать «pass» — PoC сработал на vulnerable, PoF подтвердил patched?
   Как отличить FP (GSC нашёл не ту vuln) от FN (не нашёл)?

## 5. Ограничения/контекст

- GSC готовится к **продаже** — корпус должен быть чистым (без чужих проектов с неясной
  лицензией; свои demo-apps предпочтительнее копирования чужих).
- Sandbox поднимает серверы в изолированной среде (secret-free + лимиты) — корпус не
  должен требовать внешних сервисов (DB/Redis/S3) для запуска уязвимого пути.
