# DETECTOR BRIEF — GS001

## 1. Состояние

Детектор GS001 — высокоуровневый эвристический сканер хардкод-секретов с 20+ паттернами. Текущее состояние: **TPR высокий, precision средний**. Основные проблемы:

- Паттерн `password` слишком широкий — ловит f-string-подстановки, валидаторы, документацию.
- Паттерн connection string не различает `sqlite:///` (файловая БД, легитимно) и `mysql://` (сеть).
- Паттерн `API_KEY` не фильтрует тестовые/демо-ключи (например, `sk-oh-...` — похоже на тестовый ключ OpenAI).
- Паттерн `token` ловит UUID-подобные значения (hCaptcha test token), которые уже частично фильтруются через `_is_placeholder`, но не полностью.
- Паттерн `password` ловит `password: "..."` в YAML-подобных структурах и в контексте валидации (`validate_password`).

**Ключевая статистика FP:**
- ~60% FP — `Hardcoded password` (f-string, валидаторы, тестовые значения).
- ~20% FP — `Hardcoded connection string` (sqlite:///).
- ~10% FP — `Hardcoded API key` (тестовые ключи).
- ~10% FP — `Hardcoded token` (UUID-подобные значения).

---

## 2. FP root-cause (по группам)

### Группа A: F-string подстановки (password='{password}')
**Пример:** `password='{password}'` — это шаблон для f-string, не хардкод.

**Root-cause:** Паттерн `(?:password|passwd|pwd)\s*[:=]\s*["\'][^"\']{4,}["\']` матчит `password='{password}'`, потому что `{password}` — 10 символов, попадает под `{4,}`.

### Группа B: Тестовые/демо-значения (my-super-secret-password)
**Пример:** `password = "my-super-secret-password"` — это учебный пример, не реальный секрет.

**Root-cause:** Паттерн `password` слишком широкий — ловит любые строки с дефисами и словами, которые выглядят как пароли, но не являются секретами (нет энтропии, нет спецсимволов).

### Группа C: SQLite connection strings (sqlite:///app/database.db)
**Пример:** `sqlite:///app/database.db` — это локальный файл БД, не сетевой секрет.

**Root-cause:** Паттерн `(?:mongodb|mysql|postgres(?:ql)?|redis|sqlite)://[^"\'\\s]{10,}` включает `sqlite:///`, который указывает на локальный файл, а не на сетевой ресурс с credentials.

### Группа D: Контекст валидации (password: ") # Validate the new password...)
**Пример:** `password: ")      # Validate the new password     is_valid, message = validate_p` — это не присваивание, а часть кода валидации.

**Root-cause:** Паттерн `password\s*[:=]` матчит `password:` в YAML-подобном контексте, где после двоеточия идёт не строка-секрет, а код/комментарий.

### Группа E: Тестовые API-ключи (sk-oh-BHQj5RRY9flnWdaVIkFSUwRCg8YAtGzQ)
**Пример:** `API_KEY = "sk-oh-BHQj5RRY9flnWdaVIkFSUwRCg8YAtGzQ"` — похоже на тестовый ключ OpenAI (префикс `sk-oh-` — это `sk-` + `oh-` = OpenAI test key).

**Root-cause:** Паттерн `(?:api[_-]?key|apikey|API_KEY)\s*[:=]\s*["\'][A-Za-z0-9_\-]{16,}["\']` не фильтрует тестовые ключи с известными префиксами (`sk-oh-`, `sk-test-`, `pk_test_`, `sk_live_` и т.д.).

### Группа F: UUID-подобные токены (token="10000000-aaaa-bbbb-cccc-000000000001")
**Пример:** `token="10000000-aaaa-bbbb-cccc-000000000001"` — это тестовый UUID для hCaptcha.

**Root-cause:** Паттерн `(?:token|TOKEN)\s*[:=]\s*["\'][A-Za-z0-9_\-]{16,}["\']` матчит UUID-подобные строки, которые не являются секретами. Фильтр `_is_placeholder` содержит `"00000000-"` и `"aaaa-bbbb"`, но не покрывает `"10000000-aaaa-bbbb-cccc-000000000001"`.

## 3. Precision-фиксы (таблица)

| # | Root-cause | Фикс | FP-срез | TP-риск |
|---|-----------|------|---------|---------|
| 1 | **Группа A**: f-string подстановки | Добавить в `_is_placeholder` проверку на `{` и `}` внутри значения: `if "{" in value and "}" in value: return True`. Это отсечёт `password='{password}'`, `token='{token}'` и т.д. | **Высокий** (убирает ~30% всех FP) | **Низкий** (реальные секреты не содержат фигурных скобок) |
| 2 | **Группа B**: тестовые/демо-значения | Добавить в `_is_placeholder` паттерны: `"my-super-secret"`, `"my-secret"`, `"example-password"`, `"test-password"`, `"dummy-password"`, `"fake-password"`, `"sample-password"`, `"demo-password"`. Также добавить проверку на `-password` и `password-` суффиксы/префиксы. | **Средний** (убирает ~15% FP) | **Низкий** (реальные секреты редко содержат слово "password" в имени) |
| 3 | **Группа C**: sqlite:/// | Модифицировать паттерн connection string: исключить `sqlite:///` (локальный файл) из общего паттерна. Оставить `sqlite://` только если после `//` идёт `user:pass@` (сетевое подключение). Новый паттерн: `(?:mongodb|mysql|postgres(?:ql)?|redis)://[^"\'\\s]{10,}` + отдельный паттерн для `sqlite://user:pass@host/...` | **Средний** (убирает ~10% FP) | **Низкий** (sqlite:/// — это всегда локальный файл, не секрет) |
| 4 | **Группа D**: контекст валидации | Добавить фильтр `_is_validation_context(matched)`: если после `password:` идёт не строка, а код (содержит `#`, `)`, `;`, `=`, `{`), то это не хардкод. Реализация: проверить, что значение после `:` — это строка в кавычках, а не произвольный код. | **Средний** (убирает ~10% FP) | **Низкий** (реальные секреты всегда в кавычках) |
| 5 | **Группа E**: тестовые API-ключи | Добавить в `_is_placeholder` префиксы тестовых ключей: `"sk-oh-"`, `"sk-test-"`, `"pk_test_"`, `"sk_live_"` (но `sk_live_` — это реальный ключ, осторожно!), `"test-key"`, `"demo-key"`, `"example-key"`. Для OpenAI: `sk-oh-` — это точно тестовый (OpenAI test key), `sk-proj-` — реальный. | **Средний** (убирает ~5% FP) | **Средний** (риск отсечь реальные ключи с префиксом `sk_live_` — нужно быть аккуратным) |
| 6 | **Группа F**: UUID-подобные токены | Расширить `_is_placeholder`: добавить проверку на UUID-формат `[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}` (с учётом `10000000-aaaa-bbbb-cccc-000000000001`). Если значение — валидный UUID, это не секрет (секреты не имеют UUID-формата). | **Средний** (убирает ~5% FP) | **Низкий** (реальные секреты не имеют UUID-формата) |
| 7 | **Группа B**: низкая энтропия | Добавить фильтр `_has_high_entropy(value)`: проверять, что строка содержит хотя бы 2 из 4 классов символов (строчные, заглавные, цифры, спецсимволы). `"my-super-secret-password"` содержит только строчные и дефисы — не пройдёт. | **Средний** (убирает ~10% FP) | **Средний** (риск отсечь простые, но реальные пароли типа `"correct-horse-battery-staple"`) |
| 8 | **Группа A**: шаблонные строки | Добавить в `_is_placeholder` проверку на `%s`, `{}`, `{0}`, `{1}` — уже есть `"%s%s"` и `"{}{}"`, но добавить `"{}"` (одиночные) и `"{0}"`, `"{1}"` и т.д. | **Низкий** (дополняет фикс #1) | **Низкий** |

## 4. Требует pro-проверки

1. **Фикс #5 (тестовые API-ключи)**: Префикс `sk_live_` — это реальный Stripe-ключ, его НЕЛЬЗЯ добавлять в `_is_placeholder`. Нужно проверить, какие префиксы реально используются в тестовых ключах OpenAI/Stripe: `sk-oh-` (OpenAI test), `sk-test-` (Stripe test), `pk_test_` (Stripe test publishable). Требуется валидация на реальном корпусе.

2. **Фикс #7 (энтропия)**: Порог энтропии может отсечь реальные, но простые пароли. Нужно проверить на корпусе TP: сколько TP-паролей содержат только строчные буквы и дефисы. Если >3% — фикс недопустим.

3. **Фикс #3 (sqlite)**: Нужно проверить, есть ли реальные TP с `sqlite://user:pass@host/db` (сетевое подключение). Если таких нет — можно полностью исключить `sqlite` из паттерна.

4. **Фикс #6 (UUID)**: Нужно убедиться, что нет реальных секретов в UUID-формате (например, JWT-подобные токены не являются UUID). JWT-паттерн (`eyJ...`) не пересекается с UUID, но нужно проверить.

5. **Фикс #4 (контекст валидации)**: Фильтр `_is_validation_context` может быть сложным и дать ложные срабатывания. Нужно протестировать на реальных примерах кода с валидацией паролей.

## 5. Рекомендуемая последовательность

### Фаза 1 (немедленно, низкий TP-риск):
1. **Фикс #1** — f-string подстановки (самый большой FP-срез, нулевой TP-риск).
2. **Фикс #6** — UUID-подобные токены (средний FP-срез, низкий TP-риск).
3. **Фикс #2** — тестовые/демо-значения (средний FP-срез, низкий TP-риск).

### Фаза 2 (после валидации на корпусе):
4. **Фикс #3** — sqlite:/// (средний FP-срез, низкий TP-риск, но требует проверки).
5. **Фикс #8** — шаблонные строки (дополняет фикс #1).

### Фаза 3 (требует pro-проверки):
6. **Фикс #4** — контекст валидации (средний FP-срез, но сложная реализация).
7. **Фикс #5** — тестовые API-ключи (средний FP-срез, но риск с `sk_live_`).
8. **Фикс #7** — энтропия (средний FP-срез, но риск отсечь реальные пароли).

---

**Итоговая оценка:** Фиксы #1, #2, #6 — безопасны и дают ~50% снижение FP. Фиксы #3, #4, #5, #7 — требуют валидации, но потенциально дают ещё ~30% снижение FP. Суммарное снижение FP: ~80% при допустимом падении TPR ≤ 3%.
