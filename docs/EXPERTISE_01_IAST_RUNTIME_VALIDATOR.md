# Экспертиза #1 — Runtime Exploit Validator (IAST-lite)

> **Статус:** финализирован — решения по Q1–Q6 приняты 13.08.2026 (владелец: Алексей Поляков).
> **Решение:** phased approach **D → B → F**. eBPF `--privileged` (вариант A) **отклонён** как дефолт.
> **Связано:** аудит GSC A-06/A-07, `gsc_pof_sandbox.py` (F-05), `gsc_dast_scanner.py`, `gsc_sbom.py`

---

## 1. Проблема

GSC умеет **detect** (38 детекторов), **prove** (PoC в песочнице `gsc_pof_sandbox.py`) и
**verify** (Proof-of-Fix). Но PoC выполняется в изолированном venv-песочнице и его «успех»
определяется по stdout-маркеру (`SUCCESS_MARKERS`), а **не** по факту реального
взаимодействия с уязвимой точкой в рантайме.

Следствие: PoC может «пройти», не доказывая реальную эксплуатацию (LLM печатает
`EXPLOITED` в обход уязвимости). Реальный эффект (запись в файл, сетевое соединение,
`execve`) не фиксируется.

### 1.5. Бизнес-контекст

**Почему это важно:**
- Proof-of-Fix — killer-feature для продажи (демо для CISO).
- Ложноположительный PoF («GSC говорит, что починил, а на деле нет») = репутационный риск.
- Один публичный кейс неработающего PoF подрывает доверие ко всей линейке.

**Почему это НЕ блокирует первую продажу:**
- Для демо достаточно 1–2 рабочих PoC (уже есть `sqli-demo`, `xss-demo`).
- Runtime-валидация нужна для масштабирования (100+ PoC), не для первого пилота.

**Позиция:** Phase 1 (in-process) — «nice-to-have», не блокирует продажу. Делать параллельно,
не в критическом пути.

### 2.5. Масштаб проблемы (текущее состояние)

> ⚠️ **Статус данных:** точных цифр PoC-верификации в репозитории **нет**
> (`benchmark/`, `calibration/` содержат только precision детекторов, не PoC-success).
> Раздел ниже — **методика замера**, а не измеренные факты. Цифры из внешнего отзыва
> (47 findings / 31 «прошёл» / 19 реально / разрыв 26%) **не подтверждены** и сюда не внесены.

**Что нужно замерить (до начала Phase 1):**
1. Сколько findings получают PoC (по `--with-poc` на калибровочных 10 проектах).
2. Сколько PoC «проходят» по `SUCCESS_MARKERS` в stdout.
3. Сколько из них реально эксплуатируют уязвимую точку (ручная проверка 20 случайных).
4. **Разрыв** = (п.2 − п.3) / п.2 — это и есть целевой false-positive rate PoC-верификации.

**Гипотеза причин разрыва** (проверить замером, не принимать как данность):
- LLM галлюцинирует PoC, печатающий маркер без реального эффекта;
- PoC использует mock-данные вместо реального взаимодействия;
- Sandbox-ограничения (RLIMIT_CPU, non-root) блокируют реальный эксплойт.

**Целевой KPI:** разрыв ≤ 10% после Phase 1.

## 3. Предложенный подход (из исходного предложения)

eBPF-прокси: tracepoint на `sys_enter_open` (+ read/write/connect/execve) во время выполнения
PoC в контейнере.

Код из предложения имеет **критические проблемы**:

1. **`docker run --privileged`** — снимает изоляцию, даёт PoC root-доступ к хосту. **Прямо
   противоречит F-05.** Запуск недоверенного PoC с `--privileged` = открыть дыру, которую
   GSC сам детектит (`GS031-K8S-PRIVILEGED`).
2. **`bpftool` + clang + linux-headers + CAP_BPF** — тяжёлая инфраструктура, не портируется в CI.
3. **`openai.OpenAI(api_key="YOUR_DEEPSEEK_KEY")`** — хардкод ключа (нарушение S-07).
4. Код не валиден (синтаксис), парсинг событий регэкспом по stdout.

### 3.5. Как решают конкуренты

> ⚠️ **Статус данных:** общие знания по публичным материалам вендоров, не аудит. Сверять
> перед использованием в маркетинговых/продажных материалах.

| Платформа | Подход | Изоляция | Runtime-сигнал |
|-----------|--------|----------|----------------|
| Snyk Code | Статический анализ + SCA | N/A | нет runtime-валидации |
| Checkmarx | IAST agent (в рантайме приложения) | отдельный агент | syscall hooks |
| Veracode | Sandbox + dynamic analysis | изолированный контейнер | HTTP-трафик + file I/O |
| Semgrep | Статический анализ | N/A | нет runtime-валидации |

**Вывод:** из конкурентов runtime-валидацию делают только Checkmarx и Veracode, оба —
**отдельный агент/контейнер**, а не eBPF внутри песочницы. Это подтверждает прагматичность
вариантов B (strace) и D (in-process) перед A (eBPF `--privileged`).

## 4. Открытые вопросы — РЕШЕНИЯ (13.08.2026)

**Q1. Модель угрозы → (а) PoC-код НЕ доверенный.**
GSC сканирует чужие (в т.ч. публичные) репозитории; PoC генерирует LLM (может выдать
небезопасный код). Следствие: `--privileged` категорически запрещён, мониторинг — вне
изолирующего слоя.

**Q2. Приоритет → изоляция (F-05) важнее полноты сигнала.**
F-05 — свежезакрытый инвариант; откат = откат доверия. 80% ценности дают strace/in-process
без риска. Попытка PoC сбежать сама по себе — уже finding (GS031), а не «успешная эксплуатация».

**Q3. Альтернатива → phased approach D → B → F** (детали в §7).

**Q4. Целевая среда → локальная разработка + CI (GitHub Actions).**
CI не поддерживает eBPF/CAP_BPF. Если фича не работает в CI — бесполезна для 90% пользователей.

**Q5. Минимальный набор syscalls** (по приоритету):
1. **File I/O** — open/read/write с путями вне workdir (`/etc/passwd`, `~/.ssh/`).
2. **Network** — connect к внешним IP (не localhost/127.0.0.1), socket AF_INET+SOCK_STREAM.
3. **Process execution** — execve с shell-метасимволами (`;`, `|`, `&&`), system/popen.
4. **Privilege escalation** — setuid/setgid, capset.

**Q6. Критерии приёмки** — расширены (§6).

## 6. Критерии приёмки (acceptance criteria)

### 6.1. Изоляция (F-05 не регрессирует)
- [ ] PoC выполняется **без `--privileged`** и без CAP_BPF в песочнице.
- [ ] Секреты хоста не видны PoC (`env` в PoC не содержит `DEEPSEEK_API_KEY`/`GITHUB_TOKEN`).
- [ ] Resource limits (RLIMIT_CPU, RLIMIT_AS) работают как в F-05.

### 6.2. Runtime-сигнал
- [ ] Мониторинг фиксирует ≥3 категории: file write, network connect, process exec.
- [ ] Событие привязано к `finding_key`, а не «глобальный шум».
- [ ] False-positive rate по событиям < 10% (событие ≠ эксплуатация — нужна корреляция с уязвимой точкой).

### 6.3. Производительность
- [ ] Runtime overhead < 20% (strace ~10–15%, in-process < 5%).
- [ ] Время выполнения PoC < 30 c (иначе CI timeout).

### 6.4. Совместимость
- [ ] Работает в CI (GitHub Actions, ubuntu-latest) без root.
- [ ] Работает локально (Linux, macOS) без доп. настройки.
- [ ] Python 3.9+ (target GSC).

### 6.5. Качество
- [ ] Детерминированный тест без ядра/eBPF (mock).
- [ ] Документация: как добавить новую «опасную» syscall.
- [ ] Coverage > 80% для новых модулей.

## 7. Рекомендация — phased approach (D → B → F)

**Phase 1 (1–2 недели): D — in-process monkeypatch (Python-фокус).**
Оборачиваем `subprocess.call`, `requests.get`, `open()` в `sitecustomize.py` внутри venv
песочницы; логируем факт вызова с аргументами. Покрывает ~80% Python-кейсов.

**Phase 2 (2–3 недели): B — strace для языков без in-process.**
`strace -f -e trace=open,connect,execve` на дочернем процессе (из родителя, не из контейнера);
парсим вывод, фильтруем по workdir. Покрывает JS/Go/бинари.

**Phase 3 (опционально, enterprise on-prem): F — Falco/Tetragon.**
Отдельный privileged-агент в K8s; GSC шлёт PoC в isolated pod, агент логирует syscalls.
Только после первого платящего клиента.

**Почему НЕ A (eBPF) как дефолт:** снимает F-05, требует CAP_BPF+root+clang/bpftool,
не портируется в CI (GitHub Actions без eBPF), высокая стоимость vs 80% сигнала уже закрыто B/D.

### 8.5. Что НЕ делаем (scope exclusion)

- **Не делаем** полный syscall trace (тысячи событий, шумно).
- **Не делаем** eBPF как дефолт (снимает изоляцию, не портируется в CI).
- **Не делаем** поддержку всех языков в Phase 1 (только Python/JS — 80% кейсов).
- **Не делаем** Falco/Tetragon в Phase 1 (это Phase 3 для enterprise).
- **Не делаем** авто-генерацию PoC с runtime-валидацией в одном шаге (сначала ручная проверка).
