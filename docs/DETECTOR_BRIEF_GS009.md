# DETECTOR BRIEF — GS009

## 1. Состояние

Детектор GS009 — это **обёртка над внешним CLI-инструментом** (Bumblebee от Perplexity), а не самостоятельный SAST-детектор с собственными паттернами. Он делегирует сканирование внешнему бинарнику и конвертирует JSON-вывод в находки GSC.

**Ключевые особенности текущей реализации:**
- Полностью зависит от наличия и корректной работы внешнего бинарника `bumblebee`
- Не имеет собственных regex-паттернов — все находки формируются из JSON-записей, полученных от Bumblebee
- Создаёт находки **для каждого пакета** в «интересных» экосистемах (mcp, editor-extension, browser-extension, agent-skill) — это потенциальный источник шума
- Для «неинтересных» экосистем (npm, PyPI, Go и т.д.) создаёт **одну агрегированную** находку на экосистему
- При отсутствии бинарника или ошибках — создаёт LOW/INFO находки, которые не являются security-находками по сути

**Текущее состояние:** детектор не имеет помеченных FP/TP, но архитектурно содержит несколько источников потенциального шума.

---

## 2. FP root-cause (по группам)

### Группа A: «Инфраструктурный шум» — находки, не связанные с безопасностью

**Root-cause:** Детектор создаёт находки для ситуаций, которые не являются security-проблемами:
- Bumblebee не установлен → LOW находка «Bumblebee not installed»
- Bumblebee scan failed → LOW находка «Bumblebee scan failed»
- Bumblebee timed out → LOW находка «Bumblebee scan timed out»
- Bumblebee error → LOW находка «Bumblebee error»
- Пустой результат → INFO находка «no packages found»

Эти находки не являются уязвимостями — это **операционные сообщения**. В контексте SAST-сканера они создают шум и снижают precision.

### Группа B: «Шум по интересным экосистемам» — каждая запись = находка

**Root-cause:** Для экосистем `mcp`, `editor-extension`, `browser-extension`, `agent-skill` детектор создаёт **отдельную находку на каждый пакет**. Это означает:
- Если в проекте 50 VS Code расширений — будет 50 находок
- Если в проекте 20 MCP-конфигураций — будет 20 находок
- Большинство этих расширений/конфигураций — легитимные инструменты разработчика, не являющиеся уязвимостями

### Группа C: «Агрегированный шум по стандартным экосистемам»

**Root-cause:** Для npm, PyPI, Go, Ruby, Composer, Homebrew создаётся одна находка на экосистему с сообщением вида `[npm] 150 packages found`. Это:
- Не является уязвимостью — это просто факт наличия пакетов
- Создаёт шум в отчёте: 6 экосистем = 6 находок LOW, которые ничего не говорят о безопасности
- Не содержит информации о конкретных уязвимых пакетах

### Группа D: «Отсутствие фильтрации по dev-зависимостям»

**Root-cause:** Детектор не различает production-зависимости и dev-зависимости. Для supply chain security важно:
- Production-зависимости — реальный риск
- Dev-зависимости (например, `devDependencies` в npm, `requirements-dev.txt` в PyPI) — меньший риск, т.к. не попадают в production

### Группа E: «Отсутствие фильтрации по известным/легитимным пакетам»

**Root-cause:** Детектор не имеет allowlist-механизма. Популярные, широко используемые пакеты (например, `typescript`, `eslint`, `prettier`) будут создавать находки, хотя не являются угрозой.

## 4. Требует pro-проверки

1. **Фикс #3 (dev-конфигурации MCP/agent-skill):** Необходимо проверить, какие пути Bumblebee возвращает в `source_file` для MCP-конфигураций. Если Bumblebee возвращает абсолютные пути вне проекта — фильтр по директориям может не сработать. Требуется анализ реальных примеров.

2. **Фикс #6 (dev-зависимости):** Необходимо проверить, какие значения `source_type` и `source_file` возвращает Bumblebee для dev-зависимостей. Если Bumblebee не различает dev/production — фильтр придётся реализовывать на основе анализа `source_file` (например, `package.json` → проверка секции `devDependencies`).

3. **Фикс #7 (allowlist):** Необходимо составить актуальный allowlist популярных пакетов. Слишком широкий allowlist может пропустить реальные TP (например, если популярный пакет был скомпрометирован). Рекомендуется ограничить allowlist только пакетами, которые:
   - Имеют >1M downloads/week
   - Не имеют известных CVE за последние 2 года
   - Являются инструментами разработки (не runtime-зависимостями)

4. **Фикс #4 (порог для агрегированных находок):** Необходимо определить оптимальный порог. Слишком высокий порог (например, 50) может пропустить реальные проблемы в небольших проектах. Слишком низкий (например, 5) — не уберёт шум.

5. **Общая архитектура:** Детектор полностью зависит от внешнего бинарника. Если Bumblebee не установлен — детектор создаёт LOW-находку. Это может быть приемлемо для CI-пайплайна, но в SAST-отчёте это шум. Рекомендуется обсудить с командой: должны ли операционные ошибки попадать в findings или только в логи.

## 5. Рекомендуемая последовательность

### Фаза 1: Быстрые победы (высокий FP-срез, низкий TP-риск)

1. **Фикс #1** — убрать инфраструктурные LOW-находки (Bumblebee not installed, scan failed, timed out, error)
2. **Фикс #8** — убрать INFO-находку «no packages found»
3. **Фикс #4** — добавить порог для агрегированных находок по стандартным экосистемам

**Ожидаемый эффект:** снижение шума на 40-60% без риска потери TP.

### Фаза 2: Средний приоритет (требует анализа данных)

4. **Фикс #5** — изменить сообщение для агрегированных находок (добавить «no known vulnerabilities»)
5. **Фикс #2** — allowlist известных dev-инструментов (VS Code, Cursor, Windsurf)
6. **Фикс #7** — глобальный allowlist популярных пакетов

**Ожидаемый эффект:** снижение шума ещё на 20-30%.

### Фаза 3: Требует pro-проверки

7. **Фикс #3** — фильтр по dev-конфигурациям MCP/agent-skill (после анализа реальных путей от Bumblebee)
8. **Фикс #6** — фильтр по dev-зависимостям (после анализа `source_type` от Bumblebee)

**Ожидаемый эффект:** снижение шума ещё на 10-20%, но требует валидации на реальных данных.
