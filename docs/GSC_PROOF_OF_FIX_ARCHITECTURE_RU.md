# Proof-of-Fix в GSC: архитектура доказательной верификации исправлений уязвимостей

**Версия документа:** 2.0
**Дата:** 15.08.2026
**Автор:** Алексей Поляков
**Продукт:** GSC (Git Security Checker) v1.4.0
**Статус:** для ревью (учтён технический аудит)

---

## Аннотация

GSC — самообучающаяся AppSec-платформа, реализующая полный цикл
`detect → prove → fix → verify → heal → predict`. Ключевая особенность —
**Proof-of-Fix (PoF)**: механизм, который не *предлагает* исправление, а
**доказывает** его. В статье архитектура PoF описана не через перечень модулей,
а через **три архитектурных контракта** — маркеров, изоляции и верификации, —
которые сводятся к одной формуле и определяют, что именно гарантирует вердикт
`verified`. Дополнительно показано, почему подходы конкурентов (Snyk CodeFix,
Veracode Fix) останавливаются на «предположении», тогда как PoF доводит до
«факта».

**Ключевые слова:** SAST, Proof-of-Fix, архитектурные контракты, PoC-генерация,
sandbox-изоляция, fail-closed, verified remediation.

## 1. Введение

### 1.1 Проблема: «исправлено» ≠ «доказано»

Классический SAST решает задачу *обнаружения*: находит подозрительное место и
выдаёт находку. Дальше — руками. Остаётся фундаментальный разрыв:

- **Находка может быть ложной** (false positive) — паттерн совпал, уязвимости нет.
- **Исправление может быть неполным** — закрыли один вектор, остался соседний.
- **«Закрыто» не доказано** — статус в трекере ≠ отсутствие эксплуатации.

Следствие: дорогой ручной триаж, накопление непроверенных находок, усталость от
алертов и, в пределе, — пропуск реальной уязвимости среди шума.

### 1.2 Что предлагает GSC

GSC добавляет к «обнаружению» фазу **доказательства**: для каждой находки
сгенерировать PoC (код, который *эксплуатирует* уязвимость), сгенерировать патч,
**исполнить PoC против обеих версий кода в песочнице** и зафиксировать вердикт:
эксплуатация была — эксплуатации после фикса нет. Только такое совпадение даёт
уровень `verified`.

### 1.3 Почему генерация патчей конкурентами недостаточна

Чтобы понять ценность PoF, достаточно одного принципиального различия: конкуренты
останавливаются на *генерации* патча, а PoF — на *верификации*.

**Snyk CodeFix** генерирует исправление в виде diff, но **не проверяет, что этот
diff действительно устраняет уязвимость**. Для SQL-injection он может предложить
переход на параметризованный запрос
`cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))`. Но если `user_id`
по-прежнему приходит из непроверенного источника и не проходит taint-трекинг до
конца, фикс остаётся неполным — CodeFix не исполняет код, чтобы это обнаружить.

**Veracode Fix** предлагает точечные замены (например, `eval(user_input)` →
`JSON.parse(user_input)`), но **не проверяет постфактум**, что `user_input` теперь
валиден и не несёт эксплуатируемых конструкций (вложенный SSRF, ReDoS в парсере).
Проверка «на глаз» не выполняется — система доверяет предложенной замене.

**Ключевой вывод:**

> Генерация патча — это **предположение**. Верификация через повторный PoC — это
> **факт**. GSC переходит от предположения к факту: патч считается исправленным
> только тогда, когда эксплойт, который *воспроизводил* уязвимость, *перестаёт
> срабатывать* на исправленном коде.

## 2. Proof-of-Fix как архитектурный контракт

Надёжность PoF определяется не набором модулей, а **тремя архитектурными
контрактами**. Именно они — суть архитектуры, а не синтаксис деталей реализации.

### 2.1 Контракт маркеров

PoC обязан *доказать* эксплуатацию, напечатав один из маркеров успеха:

```
VULNERABLE | EXPLOITED | PWNED | LEAKED | SUCCESS | BREACH
```

Успех PoC фиксируется **только** при одновременном выполнении двух условий:
`exit_code == 0` **и** наличие маркера в stdout. Один только нулевой код возврата
не считается — иначе PoC, который просто «завершился без ошибок», был бы ошибочно
признан эксплуатирующим. Этот контракт защищает от ложных срабатываний.

### 2.2 Контракт изоляции

Каждое исполнение PoC происходит в sandbox с ограничениями ресурсов и сети:
`RLIMIT_CPU`, `RLIMIT_AS`, `--network none`, `--read-only` и сбросом всех
capabilities (детали — §4). Контракт гарантирует: PoC **не может** прочитать
секреты хоста, исчерпать ресурсы CI или скомпрометировать окружение, в котором
работает сканер.

### 2.3 Контракт верификации

Фикс признаётся успешным **только** при строгом совпадении:

```
poc_before_success == True   И   poc_after_success == False
```

Любое отклонение — фикс неполный или находка ложная — делает результат
непроверенным. Это математическое определение `verified`.

### 2.4 Формула PoF

Три контракта сводятся к одной формуле:

```
PoF_verified = (poc_before_success == True)
             ∧ (poc_after_success == False)
             ∧ is_container_isolation(before)
             ∧ is_container_isolation(after)
```

Третий и четвёртый конъюнкты — это **fail-closed gate**: вердикт `verified`
допустим только когда обе стадии выполнены в OS-изолированном контейнере, а не в
деградированном режиме. Следствие:

> Если PoF говорит `verified` — уязвимость была воспроизведена и устранена в
> контролируемой среде, и никакой сторонний код не мог повлиять на результат.

## 3. Обзор системы и место PoF

### 3.1 Полный цикл GSC

```
detect ──► prove ──► fix ──► verify ──► heal ──► predict
```

| Фаза | Что делает |
|---|---|
| **detect** | статический анализ, 47 детекторов |
| **prove** | генерация PoC, подтверждение эксплуатации |
| **fix** | генерация патча (LLM) |
| **verify** | исполнение PoC против before/after в sandbox |
| **heal** | авто-исправление в CI (self-healing) |
| **predict** | прогнозная аналитика по истории |

Текущее состояние ядра: **47 детекторов** (43 registry + 4 standalone-движка:
Invariants GS028, Secrets GS029, SCA/OSV.dev GS030, IaC GS031), schema 33,
165 модулей, ~494K находок в SQLite-БД, 426 тестов в 75 файлах. Числа
верифицируются командой `python3 gsc_meta.py`.

### 3.2 Поток данных

```
finding + source
      │
      ▼
[PoC generation] ──► poc_code          (детерминированный или LLM)
      │
      ▼
[Patch generation] ──► patch, до MAX_ITERATIONS=3
      │
      ▼
[Sandbox]  PoC vs VULNERABLE code ──► poc_before_success
           PoC vs PATCHED code    ──► poc_after_success
      │
      ▼
[Fail-closed gate]  контракт верификации + OS-изоляция
      │
      ▼
FixEvidence: verified | structural | syntax_only | failed
```

## 4. Изоляция исполнения

Исполнение сгенерированного PoC — **критическая граница безопасности**: PoC по
определению является вредоносным кодом. GSC закрывает её двухуровневой изоляцией.

### 4.1 Контейнерная изоляция (основной путь)

PoC запускается в одноразовом контейнере (Docker или Podman) с жёстким набором
ограничений:

| Флаг | Значение | Гарантия |
|---|---|---|
| `--network none` | egress deny | PoC не может выйти в сеть |
| `--read-only` | read-only rootfs | ФС контейнера неизменяема |
| `--cap-drop ALL` | сброс всех capabilities | нет привилегий ядра |
| `--security-opt no-new-privileges` | запрет setuid | нет эскалации |
| `--pids-limit 64` | лимит процессов | нет fork-бомбы |
| `--memory 512m` / `--cpus 1` | ресурсы | нет выжигания CPU/RAM |
| `--user 65534:65534` | UID nobody | нет root внутри контейнера |
| `--tmpfs /tmp` + mount workdir | только workspace writable | запись только в свой каталог |

### 4.2 rlimit fallback (деградация)

Без контейнерного рантайма PoC исполняется как subprocess с POSIX `rlimit`
(`RLIMIT_CPU` 30 с, `RLIMIT_AS` 512 MB, `RLIMIT_NPROC` 64, `RLIMIT_FSIZE` 16 MB,
`RLIMIT_NOFILE` 256). **Важно:** rlimit — это *деградация*, а не изоляция; на
fail-closed gate результат в rlimit-режиме **никогда** не помечается `verified`.

### 4.3 Изоляция окружения

PoC получает белый список из 9 переменных окружения вместо полного `os.environ`,
что закрывает утечку секретов хоста (`DEEPSEEK_API_KEY`, `GITHUB_TOKEN`,
`JWT_SECRET`) в исполняемый PoC-код (находка DD-01 независимого аудита).

## 5. Генерация PoC и патча

### 5.1 PoC: детерминированный + LLM

Для частых классов уязвимостей (SQLi, command-injection, IDOR, XSS, SSRF,
open-redirect, а по ключевым словам — SSTI/pickle/XXE/path-traversal) PoC
генерируется **без LLM**, по жёстким шаблонам. Для остальных правил — через LLM
(`DeepSeek`, таймаут 60 с). Без `DEEPSEEK_API_KEY` система деградирует до
regex-only режима. Каждое исполнение ограничено: 30 с, вывод ≤ 4096 байт, сеть
гасится прокси-заглушкой `127.0.0.1:9`.

### 5.2 Патч: минимальность и атомарность

Патч генерируется как набор edit-instructions (пар `find`/`replace`), где `find`
обязан совпадать с текстом файла точно. Это даёт два свойства, важных для
надёжности: патч **минимален** (ревьюируем) и **атомарен** — неточное совпадение
отбрасывает попытку целиком, а не применяет кривой патч. Лимит — до 3 итераций
генерации и до 6 правок на патч; неудачная попытка передаётся в LLM как контекст
для следующей.

## 6. Цикл верификации и fail-closed gate

### 6.1 before/after PoC

Ядро доказательства — двойной прогон одного PoC:

1. **Before:** PoC против *уязвимого* кода → обязан **сработать**. Не сработал —
   вероятен false positive, вердикт отклоняется.
2. **After:** PoC против *исправленного* кода → обязан **не сработать**. Сработал —
   фикс неполный, вердикт отклоняется.

### 6.2 Fail-closed gate (GSC-001)

Финальная проверка: `verified` допустим **только** при OS-изоляции обеих стадий.
Иначе результат возвращается с явной причиной, а не с ложным «проверено». Это
принципиально: лучше честно сказать «не доказано», чем выдать необоснованный
сигнал.

### 6.3 Уровни доверия

| Уровень | Критерий | Значение |
|---|---|---|
| `verified` | PoC сработал до фикса, не сработал после, обе стадии в контейнере | доказано |
| `structural` | детектор перестал срабатывать на исправленном коде | косвенно |
| `syntax_only` | синтаксис цел, доказательств нет | слабо |
| `failed` | не удалось сгенерировать/применить/проверить | нет |

## 7. Модель безопасности и гарантии

### 7.1 Threat model

Угроза — **враждебный PoC-код**. Атакующий может пытаться: читать секреты хоста,
писать в ФС, выйти в сеть (SSRF/exfil), исчерпать ресурсы, эскалировать
привилегии.

### 7.2 Defense-in-depth

| Слой | Механизм |
|---|---|
| Сеть | `--network none` (контейнер) / proxy `127.0.0.1:9` (fallback) |
| ФС | `--read-only` rootfs, запись только в workdir, `RLIMIT_FSIZE` |
| Привилегии | `--cap-drop ALL`, `no-new-privileges`, UID nobody |
| Ресурсы | `--pids-limit 64`, `--memory 512m`, `--cpus 1`, `RLIMIT_AS` |
| Секреты | env-whitelist (9 переменных), никакого `os.environ` |
| Доверие | fail-closed gate: без контейнера — нет `verified` |

### 7.3 Гарантия вердикта `verified`

Совокупность контрактов (§2) даёт следующую гарантию: **если PoF вернул
`verified`, то уязвимость была фактически воспроизведена эксплойтом и фактически
устранена, в среде, из которой сгенерированный код не мог ни прочитать секреты,
ни повлиять на результат**. Это — главный «продукт» PoF: доверие, основанное на
доказательствах, а не декларациях.

## 9. Ограничения

1. **Языковая поддержка sandbox:** `verify_fix` исполняет только Python-PoC; для
   прочих языков возвращает `verified=False` с причиной.
2. **Зависимость от контейнерного рантайма:** без docker/podman верхний уровень
   `verified` недостижим — осознанный fail-closed выбор.
3. **LLM-зависимость глубины:** без `DEEPSEEK_API_KEY` PoC/патч генерируются
   только для шаблонных классов.
4. **Один файл за цикл:** PoF оперирует отдельным файлом, а не целым репозиторием;
   межмодульные цепочки эксплуатации — вне текущего цикла.

## 10. Дорожная карта

- **Runtime Validator (IAST-lite):** верификация по факту runtime-эксплуатации —
  monkeypatch `subprocess`/`requests`/`open` в sandbox-venv, затем `strace`
  (потребует `SYS_PTRACE`), затем Falco/Tetragon только в enterprise on-prem.
  **Без `--privileged`** — это нарушает изоляцию (F-05) и превращает PoF из
  средства защиты в вектор атаки; любой PoC, требующий `--privileged`,
  автоматически отклоняется.
- **Поддержка JS/Go/Rust** в `verify_fix`.
- **PostgreSQL + RLS** для multi-tenant SaaS (tenant isolation, DD-09).

---

## 11. Заключение

Proof-of-Fix превращает SAST из «детектора» в «машину доказанной реабилитации».
Ключевая идея — **fail-closed**: система скорее откажется подтвердить исправление,
чем выдаст необоснованный `verified`. Архитектурно это выражается тремя
контрактами (маркеры, изоляция, верификация) и одной формулой, а не списком
модулей. В сочетании с self-learning платформа движется к цели — делать
безопасность *проверяемой*, а не декларируемой.
